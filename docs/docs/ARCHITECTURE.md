## 🎯 Принципы архитектуры

### Hub-and-Spoke (Звезда)

**Фундаментальный принцип:** Все модули независимы друг от друга и подключаются **ТОЛЬКО** к центральному ядру (Core). Межмодульные зависимости ЗАПРЕЩЕНЫ.

```
                    ┌──────────────────┐
                    │      CORE        │
                    │  (Интерфейсы,    │
                    │   Контракты,     │
                    │   Данные, DI)    │
                    └────────┬─────────┘
                             │
    ┌────────┬───────┬───────┼───────┬────────┬────────┬────────┬────────┐
    │        │       │       │       │        │        │        │        │
┌───▼───┐┌──▼───┐┌─▼────┐┌▼────┐┌──▼───┐┌──▼───┐┌─▼────┐┌▼──────┐
│Charger││ Tile ││ Body ││ Qi  ││ Buff ││Inven.││Combat││Format.│
│Модуль ││Модуль││Модуль││Модуль││Модуль││Модуль││Модуль││Модуль  │
└───────┘└──────┘└──────┘└─────┘└──────┘└──────┘└──────┘└───────┘
    │        │       │       │       │        │        │        │
    └────────┴───────┴───────┴───────┴────────┴────────┴────────┘
                    ❌ ПРЯМЫЕ СВЯЗИ ЗАПРЕЩЕНЫ

    ┌───────┬───────┬───────┼───────┬────────┬────────┬────────┐
    │       │       │       │       │        │        │        │
┌───▼───┐┌▼────┐┌─▼────┐┌▼────┐┌─▼─────┐┌▼─────┐┌▼─────┐
│ NPC  ││Player││World ││Quest ││Interac.││  UI  ││ Save │
```

## 📐 Архитектурный стек

### DI-контейнер: VContainer

**Принцип:** Все зависимости разрешаются через DI-контейнер VContainer. Прямые обращения к синглтонам и ServiceLocator запрещены. Каждый модуль регистрирует свои сервисы в корневом GameLifetimeScope через паттерн ModuleServices.

**Иерархия LifetimeScope:**

```
GameLifetimeScope (корень)
├── ChargerLifetimeScope      (Modules.Charger)
├── TileLifetimeScope         (Modules.Tile)
├── BodyLifetimeScope         (Modules.Body)
├── QiLifetimeScope           (Modules.Qi)
├── BuffLifetimeScope         (Modules.Buff)
├── InventoryLifetimeScope    (Modules.Inventory)
├── CombatLifetimeScope       (Modules.Combat)
├── FormationLifetimeScope    (Modules.Formation)
├── NPCLifetimeScope          (Modules.NPC)
├── PlayerLifetimeScope       (Modules.Player)
├── WorldLifetimeScope        (Modules.World)
├── QuestLifetimeScope        (Modules.Quest)
├── InteractionLifetimeScope  (Modules.Interaction)
└── UILifetimeScope           (Modules.UI)

Дополнительные модули (ModuleServices pattern):
└── SaveModuleServices        (Modules.Save)
```

### Шина сообщений: MessagePipe

**Принцип:** Все межмодульные коммуникации проходят через MessagePipe. Прямые C#-события и обращения между модулями запрещены. Контракты сообщений — `readonly struct` для нулевой GC-аллокации. Регистрация брокеров централизована в GameLifetimeScope.

### Асинхронные операции: UniTask

**Принцип:** Все асинхронные операции используют UniTask вместо Coroutines. UniTask обеспечивает нулевую GC-аллокацию и совместимость с async/await.

## 🔄 Система времени (Time System)

### Концепция тиков

**Принцип:** 1 тик = 1 минута игрового времени

**Скорости времени:**
- Пауза — время остановлено
- Нормальная — 1 секунда реального времени = 1 минута игрового
- Ускоренная — 1 секунда = 5 минут
- Быстрая — 1 секунда = 15 минут

**Действия с точкой времени:**
- Движение — 1 тик на клетку
- Атака — 1 тик
- Ход боя — 2 тика
- Медитация — 30-480 тиков (диапазон длительности)
- Прорыв — 480 тиков (8 игровых часов)
- Разговор — 5 тиков
- Сбор ресурсов — 10 тиков

**Действия без точки времени:**
- Просмотр инвентаря
- Просмотр техник
- Просмотр статуса
- Пауза

### Структура WorldTime

| Параметр | Значение |

| Начальный год | 1864 (Э.С.М. — Эра Сердца Мира) |
| Дней в месяце | 30 |
| Месяцев в году | 12 |

**Сезоны:** Тёплый (месяцы 1-9), Холодный (месяцы 10-12)

**Время суток:** Ночь (0-4), Рассвет (5-6), Утро (7-11), День (12-16), Вечер (17-19), Сумерки (20-23)

## ⚡ Система Ци (Qi System)

### Источники Ци

1. **Микро-ядро** — естественная генерация (10% от вместимости ядра в сутки). Активируется ТОЛЬКО при пробуждении (L1+). У смертных — дремлющее ядро, Ци через медленное поглощение из среды.
2. **Медитация** — активное накопление из окружающей среды. Скорость = проводимость меридиан.
3. **Камни Ци** — внешние источники
4. **Техники поглощения** — вампиризм и подобные

### Вместимость ядра (Модель В — Растущий резервуар + Сжатие Ци)

> **Решение принято:** 2026-04-10 — Модель В выбрана как основная.
>
> См. [QI_SYSTEM.md](./QI_SYSTEM.md) — полное описание Модели В.

Каждый уровень культивации увеличивает вместимость ядра на 10% за подуровень.

**Формула:**
```
coreCapacity = 1000 × 1.1^totalSubLevels × qualityMultiplier
qiDensity = 2^(level-1)
effectiveQi = coreCapacity × qiDensity
conductivity = coreCapacity / 360

Требование прорыва = capacity(nextLevel) × density(nextLevel)
После прорыва: currentQi = 0
```

**Базовая ёмкость:** 1000 единиц Ци (L1.0)

**Рост ёмкости:**

| Уровень | totalSubLevels | coreCapacity |
|---------|----------------|--------------|
| L1.0 | 0 | 1,000 |
| L2.0 | 10 | 2,594 |
| L3.0 | 20 | 6,727 |
| L4.0 | 30 | 17,450 |
| L5.0 | 40 | 45,260 |
| L6.0 | 50 | 117,390 |
| L7.0 | 60 | 304,480 |
| L8.0 | 70 | 789,750 |
| L9.0 | 80 | 2,048,400 |

### Проводимость Ци

Характеристика, определяющая эффективность работы с Ци:
- Влияет на урон техник
- Влияет на эффективность медитации
- Может развиваться через перки (постоянно)

**Формула:** `conductivity = coreCapacity / 360`

**Формула с бонусами от перков:**
```
finalConductivity = baseConductivity × (1 + conductivityBonus)
```

**Ограничение поглощения:** Поглощение Ци НЕ может превышать проводимость меридиан:
```
absorbedQi = min(
    meditationTime × finalConductivity × environmentMult,
    availableQiInEnvironment
)
```

> **Статус реализации:** См. [ARCHITECTURE_IMPL.md](./ARCHITECTURE_IMPL.md) — раздел «Система Ци»

## 🛡️ Система баффов/дебаффов (Buff System)

### Формула модификатора

**Базовая формула:**
```
result = (base + flatSum) × (1 + percentSum / 100)
```

**Мягкий кап (soft cap):**
```
effectiveBonus = cap × (1 - e^(-bonus / (cap × decayRate)))
```

> **Источник истины:** [ALGORITHMS.md](./ALGORITHMS.md) §6

### BuffType enum

28 значений. **НЕТ** первичных характеристик (Constitution, Strength, Agility, Intelligence). **НЕТ** ConductivityBoost.

### ⛔ Что баффы НЕ могут модифицировать

| Запрещённая цель | Причина |
|------------------|---------|
| Первичные характеристики (STR, AGI, INT, VIT) | Развиваются только через действия |
| `coreCapacity` | Определяется уровнем культивации |
| `qiDensity` | Определяется уровнем культивации |
| `qiRegen` | Базовая регенерация — только от микро-ядра |

### Иммунитеты

Маппинг Effect→Immunity (BF-A03). Каждый тип эффекта может предоставлять иммунитет к определённым типам баффов.

## ⚔️ Боевая система (Combat System)

### Принцип боя

Бой происходит в реальном времени с паузой для выбора действий. Игрок может использовать техники, уклоняться, парировать.

### Порядок применения защит

> **Краткий обзор** — упрощённая схема из 6 шагов.
> Подробный пайплайн — [ALGORITHMS.md](./ALGORITHMS.md) §5

1. **Уклонение** — шанс полностью избежать атаки
2. **Парирование** — снижение урона при блоке
3. **Буфер Ци** — поглощение ЛЮБОГО урона (техники Ци и физический)
4. **Броня** — снижение физического урона
5. **Материал тела** — естественное снижение урона
6. **HP части тела** — получение урона

### Буфер Ци как защита

> **Источник истины:** [ALGORITHMS.md](./ALGORITHMS.md) §2 "Буфер Ци"
>
> Ци защищает практика от ЛЮБОГО урона — даже во сне.

**Сырая Ци (без щитовой техники):**
- Техники Ци: 90% поглощение, 3:1 соотношение, 10% пробитие
- Физический урон: 80% поглощение, 5:1 соотношение, 20% пробитие

**Щитовая техника:**
- Техники Ци: 100% поглощение, 1:1 соотношение, 0% пробитие
- Физический урон: 100% поглощение, 2:1 соотношение, 0% пробитие

### Расчёт урона техник

**Формула:**
```
finalDamage = capacity × gradeMultiplier × ultimateMultiplier
```

Где:
- `capacity` = baseCapacity × 2^(techniqueLevel-1) × (1 + mastery/100 × 0.5)
- `gradeMultiplier` = множитель Grade (common:1.0, refined:1.3, perfect:1.6, transcendent:2.0)
- `ultimateMultiplier` = isUltimate ? 2.0 : 1.0

**Факторы:**
- Базовый урон техники
- Мастерство техники (до +50% при 100%)
- Проводимость Ци практика
- Уровень культивации (множитель)
- Грейд техники (качество)
- Стихийный модификатор (см. Variant A ниже)

### Стихийные взаимодействия (Вариант А)

> **Решение принято:** 2026-04-10 — Вариант А выбран.

```
Fire ↔ Water       ×1.5 противоположный, ×0.8 сродство
Earth ↔ Air        ×1.5 противоположный, ×0.8 сродство
Lightning ↔ Void   ×1.5 противоположный, ×0.8 сродство
Light ↔ Void       ×1.5 (Void имеет две противоположности)
Fire → Poison      ×1.2 (выжигание токсинов, одностороннее)
Light → Poison     ×1.2 (очищение, одностороннее)
Void → All         ×1.2 (поглощение, существующее)
Neutral → All      ×1.0 (без бонусов)
```

> См. [ALGORITHMS.md](./ALGORITHMS.md) §10 — полная таблица.

> **Poison (Яд)** — НЕ стихия, а состояние Ци. Эффекты ядов реализуются через technique.type=poison.
> Poison не имеет противоположностей и не участвует в стихийных модификаторах ×1.5/×0.8.
> Fire→Poison ×1.2 и Light→Poison ×1.2 — единственные стихийные взаимодействия с ядами.

> **Источник истины:** [ENTITY_TYPES.md](./ENTITY_TYPES.md)

- Artifact — конструкция с простым сознанием (разумные предметы)
- Construct — конструкция + простое сознание

**Уровень 2: Morphology** — внешняя форма
- Humanoid — двурукое двуногое
- Quadruped — четвероногое
- Bird — крылатое
- Serpentine — змееподобное
- Arthropod — членистоногое
- Amorphous — бесформенное

**Уровень 3: Species** — конкретный вид
- Human, Elf, Demon, Giant
- Wolf, Tiger, Dragon
- Ghost, Elemental

### Система двойной HP (Kenshi-style)

**Функциональная HP (красная):**
- Определяет работоспособность части тела
- При 0 — часть парализована, но не отрублена
- Восстанавливается при лечении

**Структурная HP (чёрная):**
- Определяет целостность части тела
- Равна функциональной HP × 2
- При 0 — часть отрублена
- Восстанавливается медленнее

**Сердце — особая часть:**
- Только функциональная HP
- При 0 — смерть

**Распределение урона (одновременный split):**
```
redHP -= damage × 0.7     // 70% в функциональную HP
blackHP -= damage × 0.3   // 30% в структурную HP
```

> **Источник истины:** [ALGORITHMS.md](./ALGORITHMS.md) — модель одновременного split 0.7/0.3

| Материал | Твёрдость | Снижение урона |

## 🤖 Система NPC AI

### Behaviour Tree (Дерево поведения)

NPC используют иерархическое дерево поведения для принятия решений.

**Уровни дерева:**
1. **Selector** — выбор между альтернативами
2. **Sequence** — последовательность действий
3. **Condition** — проверка условий
4. **Action** — выполнение действия

### Категории NPC

| Тип | Поведение | Сохранение |
|-----|-----------|------------|
| Temp | Упрощённое AI | Только в памяти |
| Plot | Полное AI | Сохранение в файл |
| Unique | Полное AI + история | Полное сохранение |

### Spinal AI (рефлексы)

Быстрые автоматические реакции без сознательного решения:

**Трёхуровневая модель нервной системы:**
- **Уровень 1: Spinal AI** — рефлексы, скорость 1-10мс
- **Уровень 2: Neural Router** — маршрутизация сигналов, скорость 10-50мс
- **Уровень 3: Brain Controller** — сложные решения, скорость 100-500мс

**Типы рефлексов:**
- Уклонение от угрозы (Dodge)
- Отшатывание при уроне (Flinch)
- Бегство при низком HP (Flee)
- Автоматический щит Ци (QiShield)
- Настороженность (Alert)

> **Статус реализации:** См. [ARCHITECTURE_IMPL.md](./ARCHITECTURE_IMPL.md) — раздел «Система NPC AI»

## 🎒 Система инвентаря (Inventory System)

### Слоты экипировки (Гуманоид)

| Слот | Описание |
|------|----------|
| Head | Голова — шлем, шапка, корона |
| Torso | Торс — нагрудник, рубашка, роба |
| Belt | Пояс — ремень, пояс зелий, зарядник |
| Legs | Ноги — поножи, штаны |
| Feet | Ступни — сабатоны, сапоги |
| WeaponMain | Основная рука — одноручное или щит |
| WeaponOff | Вторичная рука — одноручное, щит, инструмент |
| Amulet | Амулет — с ювелирной системой |
| RingLeft1 | Кольцо левое 1 — со системой хранения |
| RingLeft2 | Кольцо левое 2 |
| RingRight1 | Кольцо правое 1 |
| RingRight2 | Кольцо правое 2 |
| Charger | Зарядник Ци — со системой зарядников |
| Hands | Перчатки — с расширением экипировки |
| Back | Плащ/спина — с расширением экипировки |

**Правила:**
- 7 видимых слотов куклы + 8 скрытых
- Максимально 4 кольца (по 2 на руку)
- 1 амулет
- 1 зарядник (форм-фактор: belt, bracelet, necklace, ring)
- Двуручное оружие блокирует WeaponMain и WeaponOff

### Принцип "Матрёшка" (Архитектура генерации)

> **Важно:** "Матрёшка" — это архитектура ГЕНЕРАЦИИ предметов, а не слои экипировки!

**Три независимых слоя генерации:**

```
┌─────────────────────────────────────────────────────────────────┐
│                    ИТОГОВЫЙ ПРЕДМЕТ                              │
│                                                                  │
│   СЛОЙ 3: СПЕЦИАЛИЗАЦИЯ (тип предмета)                          │
│   ├── sword → +crit, +speed                                     │
│   ├── axe → +damage, -speed                                     │
│   └── staff → +qiFocus, -meleeDamage                            │
│                          ×                                       │
│   СЛОЙ 2: ГРЕЙД (качество)                                      │
│   ├── Damaged → ×0.5                                            │
│   ├── Common → ×1.0                                             │
│   ├── Refined → ×1.3                                            │
│   ├── Perfect → ×1.6                                            │
│   └── Transcendent → ×2.0                                       │
│                          ×                                       │
│   СЛОЙ 1: БАЗА (материал/уровень)                               │
│   ├── Iron → 10 damage, 50 durability                           │
│   ├── Spirit Iron → 15 damage, 100 durability                   │
│   └── Dragon Bone → 20 damage, 200 durability                   │
│                                                                  │
│   Результат = Base × Grade × Specialization                     │
└─────────────────────────────────────────────────────────────────┘
```

**Применение:**
- **Экипировка:** Material (Base) × Grade × Subtype (Specialization)
- **Техники:** Level (Base) × Grade × TechniqueType (Specialization)
- **Расходники:** Level (Base) × Grade × ConsumableType (Specialization)

### Классы предметов

| Класс | Описание | Примеры |
|-------|----------|---------|
| Consumable | Расходуемые | Зелья, еда |
| Equipment | Экипировка | Оружие, броня |
| Material | Материалы | Руды, травы |
| Qi Stone | Камни Ци | Источники энергии |
| Technique Scroll | Свитки | Изучение техник |

### Грейды предметов

> **Источник истины:** [EQUIPMENT_SYSTEM.md](./EQUIPMENT_SYSTEM.md) §2 "Система грейдов"

5 грейдов экипировки (Damaged → Common → Refined → Perfect → Transcendent) и 4 грейда техник (Common → Refined → Perfect → Transcendent, без Damaged). Подробные множители и распределение — в EQUIPMENT_SYSTEM.md.

> **Статус реализации:** См. [ARCHITECTURE_IMPL.md](./ARCHITECTURE_IMPL.md) — раздел «Система инвентаря»

## 💾 Система сохранения (Save System)

### Автосохранение

**Триггеры:**
- Смена локации
- Получение новой техники
- Получение важного предмета
- Прорыв уровня
- Завершение боя

### Ручное сохранение

Игрок может сохранить игру в любой момент через меню.

### Структура файла сохранения

**Данные персонажа:**
- Характеристики (STR, AGI, INT, VIT)
- Уровень культивации
- Текущее и максимальное Ци
- Проводимость Ци
- Состояние тела (части тела, HP)

**Данные техник:**
- Изученные техники
- Мастерство каждой техники
- Назначение в слоты

**Данные инвентаря:**
- Все предметы с характеристиками
- Экипировка в слотах

**Данные мира:**
- Текущее время
- Текущая локация
- Состояние NPC
- Выполненные квесты

> **Статус реализации:** См. [ARCHITECTURE_IMPL.md](./ARCHITECTURE_IMPL.md) — раздел «Система сохранения»

## 🌍 Система мира (World System)

### Локации

Каждая локация — отдельная сцена Unity с:
- NavMesh для навигации
- Точками интереса
- NPC и монстрами
- Ресурсами

### Типы локаций

| Тип | Описание | Опасность |
|-----|----------|-----------|
| Town | Город, безопасная зона | Низкая |
| Village | Деревня | Низкая |
| Wilderness | Дикая местность | Средняя |
| Dungeon | Подземелье | Высокая |
| Sect Territory | Территория секты | Зависит от отношений |

### Переход между локациями

При переходе:
1. Сохранение текущего состояния
2. Загрузка новой сцены
3. Размещение игрока в точке входа
4. Инициализация NPC новой локации

> **Статус реализации:** См. [ARCHITECTURE_IMPL.md](./ARCHITECTURE_IMPL.md) — раздел «Система мира»

## 🖥️ Система UI (UI System)

Система UI управляет всеми элементами интерфейса: HUD, инвентарь, боевое UI, меню паузы, диалоговые окна.

**Технология:** Pure `UnityEngine.UI` (Canvas) + procedural `UIFactory`. UI Toolkit НЕ используется.

**Причина выбора legacy Text вместо TMP:** Стиль «Древний Пергамент» использует Unicode-символы (◆ ○ ★ ✓ ◇ ▰), которых нет в стандартном `LiberationSans SDF` (TMP). Legacy `UnityEngine.UI.Text` через OS-шрифты поддерживает полный Unicode.

### Ключевые компоненты UI

| Компонент | Назначение | LOC |
|-----------|------------|-----|
| `UIFactory` | Процедурное создание UI: CreateText, CreatePanel, CreatePanelWithTitle, CreateOverlayView, CreateProgressBar | ~1153 |
| `UIThemeV3` | Тема V3 «Древний Пергамент»: цвета, спрайты, промилле-размеры (1000‰ = 100%) | ScriptableObject |
| `UIFontCache` | Статический кэш шрифтов. Fallback: `Font.CreateDynamicFontFromOSFont` → `Resources.GetBuiltinResource<Font>("LegacyRuntime.ttf")`. `EnsureStaticInitialized()` логирует статус TMP при первом вызове `GetFont()` | ~750 |
| `UISpriteCache` | Кэш спрайтов темы (бордюры, орнаменты, слоты) | — |
| `UIPositioning` | Утилиты позиционирования UI (промилле → пиксели) | — |

### WireUIViews — DI-инъекция в View

`RuntimeSceneBuilder.WireUIViews()` — единая точка DI-инъекции в 22 UI View. Использует `FindFirstObjectByType<T>(FindObjectsInactive.Include)` для нахождения деактивированных панелей (WindowLayer/FloatingLayer дети стартуют с `SetActive(false)`).

**Порядок wiring:**
1. `UIThemeV3` резолвится из контейнера
2. `UISpriteCache` → wiring спрайтов в тему
3. `HUDPresenter` → `HUDPanelView`, `BuffBarView`
4. `ToastService` → `ToastView`
5. `UIThemeV3` → `HotbarPanelView`, `ContextMenuUI`
6. `MapPresenter` + drag → `MiniMapView` (ранний SetTheme для N-key)
7. `DialoguePresenter` → `DialoguePanelView`
8. `SettingsService` → `PausePanelView`
9. `UIThemeV3` → `LoadingScreenView`
10. `CharacterPresenter` / `DeathPresenter` / `CombatPresenter` → overlay Views

### CreateOverlayView + CanvasGroup (4.3)

`CreateOverlayView<T>()` создаёт stretch-fill корень с `CanvasGroup` (`blocksRaycasts=false`, `interactable=false`). Корень не перехватывает клики — только дочерние панели (`_overlay`, `_panelRoot`) управляют raycast через свои Image.

### CreateText + ContentSizeFitter

`UIFactory.CreateText()` добавляет `ContentSizeFitter` (PreferredSize H+V) + `LayoutElement` (minHeight=fontSizePx). Без этого текстовые элементы в `VerticalLayoutGroup` с `childControlHeight=false` получают `sizeDelta=0` и невидимы.

### UI Views (22 файла в Entry/UI/)

HUDPanelView, HotbarPanelView, BuffBarView, ToastView, MiniMapView, DialoguePanelView, PausePanelView, CombatOverlayView, DeathScreenView, LoadingScreenView, CharacterPanelView, TechniqueChargeView, CombatLogView, TurnOrderView, DamageNumberView, EnemyHealthBarView, InputLogPanel (#if DEBUG), NPCInspectorPanel (#if DEBUG), ContextMenuUI, GameInputAdapter, UIComponentResolver, Common/DraggableWindow.

> См. [ARCHITECTURE_IMPL.md](./ARCHITECTURE_IMPL.md) — раздел «Система UI»

## 🎬 Система сборки сцены (Scene Assembly)

### SceneOrchestrator

Оркестратор runtime-сборки сцены. Заменяет Editor-only FullSceneBuilder, обеспечивая программную инициализацию игровой сцены при запуске.

**Фазы сборки (10):**
1. CoreValidationPhase — проверка DI-резолва всех интерфейсов
2. TileMapGenPhase — генерация тайловой карты
3. WorldInitPhase — инициализация мира
4. PlayerSpawnPhase — спавн игрока (центр карты)
5. NPCSpawnPhase — спавн NPC
6. FormationInitPhase — инициализация формаций
7. ChargerInitPhase — инициализация зарядников
8. QuestInitPhase — инициализация квестов
9. UIInitPhase — инициализация UI
10. FinalizePhase — финализация сборки

**Интерфейс фазы:** `ISceneAssemblyPhase` с UniTask async поддержкой

### GameSession

Управление жизненным циклом игровой сессии:
- StartNewGame → SceneOrchestrator → Playing
- LoadGame → SceneOrchestrator (LoadMode) → Playing
- Pause / Resume
- SaveAndQuit / QuitWithoutSaving

### RuntimeSceneBuilder

Программная сборка иерархии Unity-сцены:
- Camera (Orthographic, URP 2D)
- Canvas (Screen-Space Overlay)
- EventSystem
- World Root (Grid + Tilemap + Objects)
- Player (SpriteRenderer + procedural sprite)
- Light2D (Global, для Sprite-Lit-Default)
- GameInputAdapter (F5/F9/Esc)

### ModuleServices Pattern

**Проблема:** SceneOrchestrator в корневом GameLifetimeScope видит только stub-сервисы. Реальные сервисы в дочерних LifetimeScope недоступны (sibling scope visibility).

**Решение:** Каждый модуль регистрирует свои сервисы через статический метод `XxxModuleServices.Register(IContainerBuilder)`, который вызывается из корневого GameLifetimeScope. Это решает проблему sibling scope visibility — все сервисы доступны в корневом scope.

> **Статус реализации:** См. [ARCHITECTURE_IMPL.md](./ARCHITECTURE_IMPL.md) — раздел «Система сборки сцены»

## 🎯 Система развития (Development System)

### Характеристики

**Сила (Strength):**
- Влияет на физический урон
- Влияет на переносимый вес
- Развивается через физические действия

**Ловкость (Agility):**
- Влияет на уклонение
- Влияет на скорость атаки
- Развивается через уклонения и быстродействие

**Интеллект (Intelligence):**
- Влияет на эффективность техник Ци
- Влияет на скорость обучения
- Развивается через использование техник

**Живучесть (Vitality):**
- Влияет на HP частей тела
- Влияет на регенерацию
- Развивается через получение урона и лечение

**Привязка характеристик:**

| Характеристика | Привязка | Обоснование |
|----------------|----------|-------------|
| Сила (STR) | Тело | Физическая мощь мышц и скелета |
| Ловкость (AGI) | Тело | Координация и рефлексы тела |
| Живучесть (VIT) | Тело | Выносливость и плотность тела |
| Интеллект (INT) | Душа | Ментальная сила и духовное развитие |

**Следствия привязки:**
- Тело (STR/AGI/VIT): развиваются через физические действия. При потере части тела могут временно снижаться.
- Душа (INT): развивается через медитацию и техники. НЕ зависит от состояния тела.

### Система порогов развития

Чем выше характеристика, тем больше усилий для повышения.

**Принцип:** Аналогия с ядром культивации — "чем больше сосуд, тем больше наполнять".

**Формула порога:** Базовый порог + увеличение с ростом характеристики.

### Виртуальная дельта

Накопленный прогресс, который закрепляется при сне:
- Прирост за действие: 0.001
- Максимум закрепления за сон: 0.20 (8 часов)
- Требуется минимум 4 часа сна для закрепления

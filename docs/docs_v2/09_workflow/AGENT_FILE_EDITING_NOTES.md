# Заметки: как агент работает с файлами кода (правка / размер / чтение / комментарии)

> Побочная задача владельца (24.10, final-audit follow-up): понять механику
> правок, оптимальный размер файла, формат чтения и пользу комментариев —
> чтобы осознанно дробить кодовую базу и решить fate комментариев.
> Это анализ механики агента (Z.ai Code), не изменение кода.

## 1. Как агент правит существующий файл

Механика (инструменты платформы):

| Инструмент | Что делает | Когда используется |
|---|---|---|
| Read | Чтение файла (до ~2000 строк за вызов; длинный вывод сохраняется во внешний файл и читается кусками с offset/limit) | ВСЕГДА перед правкой — обязательный шаг |
| Edit | Точечная замена: найти уникальную строку/блок → заменить только его | Основной инструмент правок |
| MultiEdit | Серия замен за один вызов | Несколько правок в одном файле |
| Write | Перезапись файла ЦЕЛИКОМ | Новый файл или изменение >~60% содержимого |
| Bash (sed/python) | Массовые/регулярные правки | Переименования по многим файлам |

**Ответ на вопрос: переписываю ли файл целиком?** Нет. Стандартный цикл —
«Read → Edit/MultiEdit»: заменяются только изменённые фрагменты, остальной
файл не переписывается и не рискует быть случайно потерянным. Полная
перезапись — исключение (новые файлы, тотальная реструктуризация).

Следствие: цена правки = цена чтения (найти якоря) + цена диффа.
**Чтение — доминирующая затрата.** Это ключ к остальным выводам.

## 2. Оптимальный размер файла кода

| Размер | Оценка | Почему |
|---|---|---|
| 100–400 строк (~3–15 КБ) | Оптимум | 1–2 чтения целиком; якоря правок уникальны; диффы дешёвые |
| 400–800 строк | Рабочая зона | 2–3 чтения; ещё комфортно |
| 800–1500 строк | Деградация | Каждая правка = несколько чтений; якоря теряют уникальность (Edit падает, приходится расширять контекст); каждый цикл «правка→проверка» дорожает |
| >1500–2000 строк | Анти-оптимум | Почти каждое касание — многократное чтение; высокая цена любой мелкой правки; рост ошибок контекста |

Практические пороги (эмпирика этой сессии):
- делить файл при **>600–800 строк или >25–30 КБ**;
- один класс/сервис = один файл (уже соблюдается структурой `Modules/<Домен>/`);
- пример на грани: `Stage18SubsystemIntegrationTruthSimDebug.cs` — 1078 строк;
  правка этой сессии потребовала 2 чтения + 7 точечных замен. Ещё +300 строк —
  и каждое касание станет заметно дороже. Сим-файлы этапов можно дробить
  на «сценарии в отдельных файлах» при следующем серьёзном расширении.

## 3. Один большой файл или несколько мелких — что лучше для чтения

**Несколько малых/средних — лучше.** Причины:
- навигация идёт по именам и поиску (glob/grep): агент читает только нужное;
  большой файл вынуждает читать нерелевантные части;
- поиск по большому файлу шумит (много совпадений), по малым — точный;
- в малых файлах уникальнее якоря правок — меньше падений Edit;
- при дроблении параллельные правки разных файлов независимы.

**Но не дробить до пыли**: файлы <50–80 строк дают обратный эффект —
фиксированная цена каждого «открыть/прочитать» и прыжки по 20 файлам ради
одной задачи. Оптимум — **одна ответственность на файл, 100–400 строк**,
предсказуемые имена и плоская структура каталогов
(текущая схема `Modules/<Домен>/<Сервис>.cs` уже близка к оптимуму).

Отдельный класс — append-only файлы (worklog.md): их размер почти не влияет
на цену ДОПИСЫВАНИЯ (читается хвост/превью), но влияет на полное чтение.
Держать секции короткими, со стабильными заголовками и маркерами `NEXT:`.

## 4. Нужны ли комментарии — и какие

**Да, комментарии читаются и активно используются.** Комментарий — главный
носитель «почему» (код показывает только «что»): инварианты, единицы (‰,
минуты, тики), условия воспроизведения, ссылки на канон (этапы аудита,
ID дефектов, параграфы задания). В культуре ЭТОГО проекта комментарии
нагружены контрактной информацией (ST18-004, §3 F, FA-1…) — по ним агент
восстанавливает смысл теста без повторного вывода. Это «несущая
конструкция» будущих сессий, а не украшение.

Классификация и судьба:

| Тип комментария | Нужен агенту? | Рекомендация |
|---|---|---|
| Контракт/инвариант («почему», единицы, ограничения) | Да, критично | СОХРАНИТЬ |
| Ссылки на канон (этап, ID дефекта, параграф) | Да, критично | СОХРАНИТЬ |
| Заголовок файла (что это, как запускать) | Да | СОХРАНИТЬ (можно ужать до 5–15 строк) |
| История правок в теле («исправлено там-то тогда-то», построчные даты) | Нет — дублирует git log | МОЖНО УДАЛЯТЬ |
| Повествование, повторяющее очевидный код | Частично | МОЖНО УЖИМАТЬ |

Ответ на вопрос «удалять ли комментарии, оставив минимальные описания
файлов»: **массовое удаление не рекомендуется** — потеря контрактов и
инвариантов заметно удорожает будущие аудиты/правки (агент будет заново
выводить смысл) и повышает риск регрессий. Безопасная альтернатива —
**ленивая чистка**: при каждом следующем касании файла удалять только
исторические/повествовательные комментарии, контракты не трогать.
Ожидаемая экономия от полной зачистки ~15–30% токенов на чтение —
не оправдывает риск потери доменной логики.

## 5. Итоговые рекомендации для Ai-game4

1. Структуру не ломать: `Modules/<Домен>/` + `Adapter/` уже оптимальны.
2. Монстров (>800 строк) делить при следующем серьёзном касании, не отдельной задачей.
3. Новые файлы — держать в 100–400 строках; сим-файлы этапов при росте дробить по сценариям.
4. Комментарии-контракты сохранить; историю правок вычищать лениво; минимальный заголовок файла обязателен.
5. Worklog — append-only, короткие секции, `NEXT:`-маркеры (уже соблюдается).

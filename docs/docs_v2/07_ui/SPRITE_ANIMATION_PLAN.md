## 4. Целевая модель спрайтов (стандарты)

### 4.1 Формат кадра и листа

| Параметр | Значение | Обоснование |
|---|---|---|
| Кадр (working) | **64×64 px**, PNG, RGBA, прозрачный фон | равен TILE_PIXELS=64; поля под замах/экип; кадр демо 64×64; тело 48×48 центрируется внутри с полями |
| Source (генерация) | 1024×1024 на одиночный спрайт; **1344×768 / 1440×720** на лист-полосу (4–6 кадров); 1024×1024 на сетку 5×N (направления) | поддерживаемые размеры z-ai; пайплайн SPRITE_PIPELINE (NEAREST-даунскейл) |
| Body-бокс в кадре | тело ≈ 48×48 по центру: голова y≈14, стопы y≈58, центр (32,32) | сохраняет совместимость композита: правая кисть ≈ **(+6,+6) от центра** — якорь MainHand |
| Фильтр | NEAREST (Point) | канон §2.2 SPRITE_CATALOG + project.godot |
| Лист | полоса «1 анимация × 1 направление × N кадров» (этап 1) → сетка «5 рядов-направлений × N кадров» (этап 2, как демо) | одна генерация = один лист → внутри-листовая консистентность |
| Именование | `player_{anim}.png` (лист), `player_{anim}_{dir}.png` при 5-рядной сетке; кадры нарезаются кодом (`Hframes/Vframes/Frame`), отдельные кадры в файлы НЕ раскладывать | snake_case, префиксы §20.2 SPRITE_CATALOG |
| Каталог файлов | `game/resources/sprites/characters/player/`, `…/npc/`, `…/animals/`, `…/equipment/{icons,equipped}/`, `…/items/` | расширение §20.1 SPRITE_CATALOG + контракт PNG-миграции PROCEDURAL_SPRITES §5 (тот же ключ кэша) |

### 4.2 Направления (этапы)

- **Этап D1 (обязательный, 0 правок логики):** 1 направление (вправо) × FlipH =
  2. Текущая facing-модель бинарная (порог 0.15) — листы «вправо» ложатся в
  код как есть.
- **Этап D2 (расширение):** 5 рядов (front / front-¾ / side / back-¾ / back) ×
  FlipH = 8 — эталон демо, соответствует 8-направленному движению. Требует
  октантную facing-модель (вектор движения → ряд 0..4; ~10–15 строк в
  `HandleFreeMovement` + `Frame = dir*N + progress` в аниматоре) — отдельная
  код-задача (§11, точка I-3). Все листы этапа D1 остаются рядом «side» (2).

### 4.3 Анимационные параметры

| Параметр | Значение |
|---|---|
| Частота | канон §17: 10–15 fps; уточнение: idle 6–8, walk 10–12, run 14–15, melee 15 |
| Синхрон атаки | melee-лист = **6 кадров @ 15 fps = 0.4 с** ≈ `MainHandSwingSec=0.42` (кадр замаха совпадает с выпадом оружия) |
| Зацикливание | idle/walk/run/meditate/guard/sleep — loop; melee/bow/cast-release/hit/death/dash/breakthrough — one-shot (последний кадр death — hold) |
| Множители скорости | Shift-бег ×1.8 (ускорение прокрутки кадров, НЕ замедление как в демо); gameSpeed Fast ×2 / Quick ×3.5; пауза — стоп-кадр |
| Движок прокрутки | код в физ-тике (60 Гц): `progress += fps×delta×multiplier % N; Frame = dir×N + progress` — паттерн `PlayerSprite._Process` демо |

### 4.4 Якоря и совместимость с композитом (НЕНАРУШИМЫЕ условия)

1. Правая кисть тела в кадре — локально **(+6,+6) от центра** (48×48-бокс):
   сюда указывает `HandOffset` 1H (+14,-6) от центра спрайта. ПриFlipH оружие
   зеркалится кодом — лист рисуется только «вправо».
2. Стопы — на стабильной базовой линии: bounding-box низа тела ±2 px во всех
   кадрах листа (иначе «прыгающая» походка).
3. Тело не выходит за 48×48-бокс по X (поля — под замах/эффекты).
4. Без тени в арте (тень — отдельный код-эллипс 32×16), без текста/рамок.
5. Силуэт читается при 64×64 на экранном 144 px (zoom 3) — проверка
   downscale-превью до приёмки.

вариантов). Этап D2 (8 направлений): те же листы сеткой 5×N = ~270 кадров
(генерировать сеткой 5 рядов × N колонок одним изображением на анимацию —
13 генераций сеток, НЕ 65 отдельных).

### 5.2 Уровни культивации

9 уровней → цвет ауры (§4.5): тинт/VFX-каналом, отдельные комплекты листов НЕ
генерируются. Варианты `player_variant*` (SPRITE_CATALOG §5, 8 шт.) —
опциональная косметика позже (G5+), не блокирует ничего.

### 5.3 Минимальный жизнеспособный набор (MVP)

`player_idle` + `player_walk` + `player_meditate` + `player_death` —
4 листа / 20 кадров: закрывает 90 % экранного времени и два самых заметных
пробела (медитация-стоя и смерть-телепорт).

## 6. Набор спрайтов NPC

### 6.1 Стратегия: базовое тело + перекраска роли

NPC-роли визуально различаются сейчас только цветом (процедурная палитра
§3.2). Сохранить эту семантику дёшево:

- **1 базовый комплект листов гуманоида** (муж. силуэт; жен. — G4 опционально):
  `npc_idle` (2–4), `npc_walk` (4–6), `npc_melee` (4), `npc_cast` (3, только
  культиваторы), `npc_hit` (2), `npc_death` (3) — **≈ 20–24 кадра / 5–6 листов**.
- **Роль = перекраска** через image-edit по референсу базового листа
  («recolor robe to …, keep pose/shading») — 8 ролей × (idle+walk) =
  **16 эдитов**; melee/cast/death можно оставить в базовом цвете (бой —
  дистанция, различие некритично) → оптимум **~6 генераций + 16 эдитов**.
- Канонные имена `npc_*` (SPRITE_CATALOG §6, 18 шт.) остаются целевыми именами
  ФАЙЛОВ; соответствие роль→файл — таблица §6 там же. Специальные силуэты
  (`npc_enemy_demonic`, `npc_rival`, `npc_fairy`, `npc_beast_cultivator`) —
  отдельные генерации G5 (4 листа idle+walk).

### 6.2 Звери

| Вид | Листы | Кадров | Примечание |
|---|---|---|---|
| wolf | idle 2 / walk 4 / run 4 / attack 2 / death 1 | 13 | враг №1 (Monster-спавн диких локаций) |
| deer | idle 2 / walk 4 / run 4 / death 1 | 11 | мирный, стадо |
| rabbit | idle 2 / walk 4 / run 4 / death 1 | 11 | малый, бегство |

Боковой силуэт (направление «вправо» + FlipH) — звери боковые по природе,
D2-направления для них низкоприоритетны. Итого ~35 кадров / ~9 листов / 9
генераций (+ варианты отбора). Остальные 10 видов SpeciesRegistry — не
спавнятся (§3.2), НЕ генерируются до появления в спавне.

### 6.3 Трупы и предметы

- Труп: 2 варианта `corpse_human` / `corpse_beast` (лежащая поза, 1 кадр
  64×32) — G5; до того остаётся канон-маркер «саван» (уже работает, лут-бейдж
  сохраняется).
- Предметы на земле: остаются категорийными иконками 16×16 (уже есть);
  bob-анимация — кодом (позиц. синус), спрайты не нужны.

### 6.4 Вариативность однотипных NPC (перспектива)

Сейчас NPC одной роли неотличимы (кэш по роли). После PNG-миграции: выбор
варианта по seed NPCId (2–3 варианта перекраски/причёски на роль через
edit-варианты) — код-задача §11 I-6, ассеты — дополнительные эдиты.

### 6.5 Итог по объёмам NPC

| Уровень | Состав | Кадров | Генераций+эдитов |
|---|---|---|---|
| Минимум | 1 база (idle/walk) + 8 перекрасок + 3 зверя (idle/walk) | ~50 | ~8 + 8 |

## 7. Оружие: PNG-миграция (точечное крепление — сохранить)

Механика R15 (крепление, оффсеты, замах, зеркалирование) **остается как есть**
— она и есть «натягивание» для оружия. Меняется только источник текстур:

| Спрайт | Сейчас | Цель |
|---|---|---|
| Icon 32×32 | процедурный `CreateWeaponIcon` | PNG 32×32 (`equipment/icons/weapon_{class}_{tier}.png`) |
| Hand 48×48 | процедурный `CreateWeaponHandSprite` (диагональ 45°, рукоять G=(16,36)) | PNG 48×48 с той же геометрией рукояти/диагонали (`equipment/equipped/…`) |

- Консистентность: **1 генерация на класс** (7 шт. — «icon-вид» и «hand-вид»
  отдельно) + 4 материала как image-edit перекраски по референсу →
  7×2=14 генераций + 56 эдитов покрывают все 35 комбинаций.
- Золотая обводка Legendary/Mythic — остаётся кодом (`ApplyGoldenOutline`).
- Ключи каталога (class|tier|rarity) и fallback-цепочка — не меняются:
  PNG-миграция по контракту PROCEDURAL_SPRITES §5 (тот же ключ кэша, рендерер
  не переписывается).
- Анимация атаки: оружие качается вместе с телом (выпад уже кодом) +
  поза-кадры `player_melee` — отдельные кадры оружия НЕ генерируются.

## 8. Броня: анализ «натягивания» спрайтов на персонажа/NPC

### 8.1 Вариант A — полный покадровый paperdoll (слой на каждый кадр)

Каждый слот брони — overlay-текстура, выровненная по каждому кадру каждой
анимации. Объём: 6 слотов × 52 кадра (D1) = **312 overlay-кадров**, ×5 тиров =
**1560**; при D2 (8 направлений) — ×5 рядов = **7800**. Генерационно
нереально (нестабильность позы между генерациями → «прыгающая» броня),
поддержка — ручная подгонка каждого кадра. **ОТКЛОНЁН.** (Легаси-дрефт
EQUIPPED_SPRITES_DRAFT предлагал «1 слот = 1 предмет = 1 equipped-спрайт» для
СТАТИКИ — та же комбинаторика при анимациях.)

### 8.2 Вариант B — стикеры на оффсеты (как оружие)

Мини-спрайт брони у части тела (аналог HandOffset). Дёшево, но семантически
неверно: «шлем-стикер» и «сапоги-стикер» читаются плохо, при walk ноги
меняют позу — стикер статичен. Годен как переходный и для БЕЙДЖЕЙ
(зарядник на поясе — свечение, §8.4). **Частично.**

### 8.3 Вариант C — гибрид (РЕКОМЕНДАЦИЯ)

| Слот | Механика | Ассеты |
|---|---|---|
| **Torso** (нагрудник/роба/кольчуга) | **полно-кадровая замена тела**: листы `player_{anim}_armor_{tier}` — тот же персонаж в броне; выбор листа по материалу надетого торса. Генерация: базовый armored-лист (по референсу одобренного `player_walk`) + 4 материала эдитами | 5 комплектов ×(idle+walk+melee) = 15 листов ≈ 15 генераций/эдитов (G4) |
| **Head** (шлем/капюшон) | стикер-оверлей на якоре головы (центр + (0,-18) от центра кадра), 3 ракурса-смещения не нужны на D1 | 6 PNG 24×24 (3 формы × 5 тиров эдитами) |
| **Feet** (сапоги) | стикер на стопах: 2 позы ног walk (шаг/перекат) + idle = **3 кадра** на тир | 15 PNG 24×16 |
| **Legs** (поножи) | тинт-зона: перекраска нижней трети тела (palette-map кодом) либо стикер как feet | 0–5 PNG |
| **Belt** (пояс/зарядник) | стикер-полоса + для зарядника уже есть бейдж-механика | 5 PNG 32×12 |
| **Hands** (наручи) | тинт рук (код) | 0 PNG |

Правило приоритета заметности (порядок реализации): Torso → Head → Feet →
Belt → Legs/Hands. В скрытых состояниях (cast/meditate/sleep/death) броня
упрощается: torso-вариант берётся из idle-комплекта (позы статичны —
допустимо), стикеры — от idle-якорей.

### 8.4 Z-порядок и события (интеграционные условия)

- Игрок: тень 3 → тело 4 → **броня-слои 5** → **MainHand сдвинуть 5→6** →
  аура 9. Порядок слоёв согласован с RENDER_LAYERS §3.5 (Shadow −1 → Visual 0
  → Equipped 1..N) и SlotSortingOrder легаси-дрефта (Feet→Legs→Belt→Torso→
  Hands→Head→WeaponOff→WeaponMain).
- Событие готово: `EquipmentChangedEvent` уже несёт Slot+ItemId — расширить
  фильтр GWC:2415 со «WeaponMain/Off» на все видимые слоты (+ страховка-пулл
  0.5 с уже существует).
- NPC: вставка брони = 1–2 `DrawTexture` между телом и оружием в
  `NPCSpriteRenderer._Draw` (порядок draw уже канонизирован); полл 0.5 с уже
  тянет ВСЕ слоты; **ключовать по слоту, не по item.Slot** (§3.3: NPC-броня
  генерится вся как Torso).
- UI: иконки брони 32×32 (те же PNG) → хотбар/кукла/инвентарь — оживить
  мёртвый `CreateEquipmentIcon`-контракт иконками (код-задача §11 I-8).

## 10. Условия и чек-лист приёмки (обязательные)

### 10.1 Технические

- [ ] Кадр после нарезки ровно 64×64 (или 24×24/32×32 для стикеров/иконок);
- [ ] Прозрачный фон (генерация на чёрном → вырезание PIL §6.2.4
      SPRITE_PROMPTS_OBJECTS);
- [ ] NEAREST-даунскейл (никакого сглаживания краёв);
- [ ] Базовая линия стоп: низ bounding-box ±2 px по всем кадрам листа;
- [ ] Якорь правой кисти (+6,+6) от центра — для совместимости MainHand;
- [ ] Тело в 48×48-боксе по X (D1);
- [ ] Кадров в листе = спецификации §5.1/§6 (счётчик нарезчика);
- [ ] fps-контракт: walk ≥ 10, melee = 6 кадров (0.4 с ≈ 0.42 с замаха);
- [ ] Проверка «в мире»: превью на zoom 3 (144 px) поверх биом-тайла.

### 10.2 Стилевые

- [ ] Pixel art, top-down 45°, без полутонов-градиентов;
- [ ] Палитра в окрестности якорей §4.5 (допуск ±15 % на тон);
- [ ] Один и тот же персонаж между листами (identity-якорь промпта);
- [ ] Нет тени/текста/рамок/фона в арте.

### 10.3 Консистентность генерации (главный риск)

- [ ] Один лист = одна генерация (кадры не склеиваются из разных генераций);
- [ ] Последующие листы того же персонажа — через **image-edit от одобренного
      idle-кадра** («same character, walk cycle…»), не «с нуля»;
- [ ] Перекраски (роли/материалы) — только edit-каналом по референсу;
- [ ] Ревью: силуэт в 64×64 различим от соседних архетипов (guard vs passerby).

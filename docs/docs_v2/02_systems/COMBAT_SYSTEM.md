# Боевая система (Combat System)

> **Назначение:** Документ описывает механику сражений: real-time-with-pause, tick-based симуляцию, 11-слойный конвейер прохождения урона, типы атак, эффекты стихий, оглушение/кровотечение/смерть. Документ engine-agnostic: описаны только концепции, формулы и данные — без привязки к движку.

**Связанные документы:** `02_systems/BODY_SYSTEM.md`, `02_systems/QI_SYSTEM.md`, `02_systems/TECHNIQUE_SYSTEM.md`, `02_systems/ELEMENTS_SYSTEM.md`, `02_systems/FORMATION_SYSTEM.md`, `09_workflow/ALGORITHMS.md`.

## 1. Обзор и принципы

### 1.1. Принципы боя

1. **Игровое состояние — источник истины.** Игра полностью однопользовательская, все боевые расчёты выполняются локально.
2. **Действия измеряются в тиках.** 1 тик = 1 игровая минута. Бой ведётся в реальном времени с возможностью паузы.
3. **Порядок применения защит важен.** Защиты применяются строго в определённой последовательности.
4. **Ци — первый уровень защиты от ЛЮБОГО урона** (даже во сне).

### 1.2. Real-time with pause

- Бой происходит в реальном времени; игрок может поставить паузу в любой момент.
- При начале боя автоматически включается режим `superSuperSlow` (очень медленная скорость симуляции, ~0.25 минут/тик).
- Скорости симуляции: pause=0, normal=1 tps, fast=5 tps, quick=15 tps.
- См. `03_world/TIME_SYSTEM.md` для деталей системы тиков.

### 1.3. Tick-based, а не physics-driven

Бой НЕ использует физический движок (нет rigidbody-солвера). Все попадания, движение снарядов, AoE рассчитываются формульно через тайлы и тики. Это обеспечивает:
- Детерминизм симуляции.
- Низкие накладные расходы (battle logic работает в pure-C# модулях, тестируется через `dotnet test`).
- Простоту AI (decision per tick, а не per frame).

### 1.4. Модель боя 1v1 и ГОТОВНОСТЬ удара (R21-2, фиксация 2026-09-20)

> R21-2 (репорт 20.09 №2): ходовая модель **удалена** — удары НЕЗАВИСИМЫ.
> Замена: модель готовности (readiness, attack-speed). Прежняя схема
> («владение ходом», чередование ударов 1:1, EnemyTurnTimeout 2.5с) жёстко
> блокировала игрока «ходом противника» даже с готовым мечом — решение
> пользователя: темп боя задаёт ОРУЖИЕ.

#### 1.4.0. МУЛЬТИБОЙ «реестр входов» (R24-C, 2026-09-21, выбор пользователя)

> План: checkpoints/plans/2026-09-20_r23_multicombat_aoe_design.md §1-C
> (вариант C «реестр входов»; B «per-pair сессии» — целевая миграция,
> «надстройка» +1-2 эпизода). Исследование DF/RimWorld/M&B: §6.1 плана.

- **Гейт участника 1v1 УДАЛЁН** (корень CMB-2: эмерджентная стычка
  NPC-NPC где угодно на карте занимала единственный слот боя и
  блокировала атаки игрока «не участник»). Атака разрешена ЛЮБОЙ паре
  живых сущностей: толпа бьёт игрока, игрок бьёт толпу, NPC дерутся
  между собой.
- **«Слот» боя = UI-сессия игрока** (`_isInCombat/_instigatorId/
  _currentTargetId/_currentStage`, CombatStarted/EndedEvent, HUD-пара,
  таймаут MaxCombatDuration). Открывает её ТОЛЬКО пара с участием
  игрока (CombatModule+CombatService гейт `pairHasPlayer`).
- **NPC-vs-NPC дерутся «молча»**: урон идёт тем же 11-слойным пайплайном,
  месть — per-target (`NPCAIService.OnDamageApplied → RetaliateOrFlee`),
  труп — `NPCCombatAdapter.OnDamageApplied → NPCDeathEvent`. БЕЗ
  CombatStarted/стадий/таймаута — стычка живёт до смерти/бегства по
  HP-правилам AI (RimWorld/DF-модель «скрытой жизни мира»).
- **Реестр дерущихся живёт без привязки к UI-бою:**
  `_readinessPermil`/`_pendingCasts` тикают ВСЕГДА (UpdateTimer без
  `!_isInCombat`-гейта). EndCombat чистит ТОЛЬКО участников UI-пары
  (RemoveFighter; чужие тихие касты продолжают резолвиться). Мёртвые
  выбывают из реестров при смерти.
- **Незарегистрированная сущность = «инициатор»** (GetReadinessPermil →
  Threshold; запись заводится при ConsumeReadiness) — иначе первый
  интент свежей NPC-пары deadlock-ился гейтом IsAttackReady.
- **Defender-резолв** (`ResolveDefenderIdFor`): участнику UI-боя — пара
  (инстагатор→цель слота, цель→инстагатор; прежняя семантика M1/A3-3);
  не-участнику — ЗАЯВЛЕННАЯ цель интента (толпа бьёт игрока по своему
  выбору, NPC-NPC — свою цель).
- **Смерть не-участника UI-пары — тихая:** труп/месть по событиям
  (per-target), UI-бой завершается только если погиб участник UI-пары
  (или игрок). EnemyKilledEvent — по-прежнему «убил игрок».
- QA: COMBAT_SIM 3g — (a) тихий NPC-NPC без UI-сессии + месть (Threats),
  (b) сессия пары с игроком, (b2) **CMB-2-регресс: не-участник бьёт
  игрока в активном UI-бое** (Accepted + урон).

- **Готовность (readiness, промилле) — авторитетный гейт.** Каждый тик боя каждому участнику начисляется скорость атаки (§8.2); при `readiness ≥ AttackThresholdPermil (1000‰)` удар принимается (`Accepted`) и вычитает порог. Удар при неготовности отклоняется («удар не готов (X‰ < 1000‰)» — `AttackRejectedEvent` для игрока; NPC молча ретраятся). Расход готовности — только при ПРИНЯТИИ (отвергнутый гейтами удар не теряет готовность). Кап = порогу («банковать» залп замахов нельзя).
- **Инициатива у инициатора боя:** кто начал бой — тот начинает с полной готовностью (первый удар сразу), защитник — с нулевой.
- **Касты per-attacker** (R21-2): каждый участник кастует СВОЙ удар (словарь `_pendingCasts`); чужой каст НЕ блокирует атаку (прежде — combat-wide pending: пока кастовал NPC, атака игрока отвергалась «Каст уже идёт»). Гейт LOS/стрел (CombatModule) проверяет каст ИМЕННО атакующего (`IsEntityCasting`).
- **CLASH — одновременная атака → парирование** (решение пользователя 20.09): если удар прилетает, пока ЗАЩИТНИК в замахе (его собственный pending-каст) — «клинки скрестились»: удар парируется гарантированно (урон ×0.5, слой 5), замах защитника НЕ отменяется и готовность не тратится (уже потрачена на замах). Уклонение/крит сильнее (обрабатываются раньше форса). Обычные удары стойкой выбора НЕ блокируются («пока не блокируемые») — только одновременность скрещивает клинки.
- **Целью боя управляет только игрок** (и только переключение на не-участника); NPC-интенты глобальную цель не меняют.
- **NPC-атаки идут через реальных сущностей** (`NPCModule.ProcessNpcAttacks`, гейт `IsAttackReady`); отдельного «AI противника» (`CombatAIService`) больше нет.
- **Расход стрел (ammo) — транзакция:** списание только после принятой атаки (`Accepted`), проверка наличия — до начала боя.

#### 1.4.1. Боевой ИИ NPC (R16, 2026-09-10)

Реализация «рабочего боя игрок↔NPC» — переходы ИИ ДО гейта `IsInCombat` в
`NPCAIService.EvaluateAndDecide` (раньше NPC в бою не менял состояние вообще):

- **Месть/ответ:** удар по NPC или старт боя → `Attacking` (боец) или
  `Fleeing` (миролюбивый: Pacifist/Cautious-гражданский). Эвристика
  `ShouldFleeInsteadOfFight`: роли Guard/Enemy/Monster и черты
  Aggressive/Vengeful дерутся всегда; остальные гражданские — по чертам.
  ДО R16 NPC, атакованный игроком, оставался «манекеном» (IsInCombat без
  Attacking → ProcessNpcAttacks не видел цели).
- **Бегство в бою (§4.2 NPC_AI_SYSTEM):** HP ≤ `FleeHealthRatio` (20%)
  работает и В БОЮ → `Fleeing` + `CombatDisengageEvent` → бой завершается
  стадией Flee («никто не победил»). Раненый NPC не пере-агрится
  (гейт healthRatio на пути угроз — иначе flip-flop агро↔бегство).
- **Leash (aggro-drop):** цель-игрок дальше `AggroRadius×3` (15 тайлов) →
  NPC выходит из боя (`CombatDisengageEvent`) → игрок может спастись
  бегством. Раньше преследование было вечным.
- **Активная защита NPC:** `NPCDefenseSelector` (pure-C#, детерминизм) —
  щит (WeaponOff) → `Block`; оружие и STR>AGI+4 → `Parry`; прочие →
  `Dodge`. CombatService подставляет выбор в слой §7 для каждой атаки по
  NPC (заодно чинит NPC-vs-NPC: защитник-NPC раньше получал стойку игрока).
- **Kiting лучников:** дальнобойное NPC (AttackRange>2) держит дистанцию:
  dist<3 → отход, dist≤AttackRange → стоит и стреляет (ближний бой — как
  раньше, сближение до AttackRadius).
- **Единственный источник `CombatStartedEvent`** — `CombatService.StartCombat`
  (первый принятый интент). `MarkNpcCombatStarted` помечает состояния
  напрямую, БЕЗ фантомного publish (раньше — двойное событие при реальном
  старте).
- **Гашение каста при завершении боя (аудит R16, P1-1):** бегство/leash
  (AbandonCombat) может завершить бой ПОСЕРЕДИ чужого каста — EndCombat
  гасит `_isCasting`/`_pendingTechnique`; иначе гейт «Каст уже идёт»
  отклонял бы все новые атаки, а анти-лок EnemyTurnTimeout отключён
  условием `!_isCasting` → перманентный лок боевой подсистемы.
- **Сброс стойки игрока при конце боя (аудит R16, P3-2):**
  PlayerCombatAdapter сбрасывает `CurrentDefenseStance=None` на
  `CombatEndedEvent` (синхронизация с `_lastPlayerDefense` CombatService —
  иначе G-цикл нового боя шёл от «призрачной» стойки).
- **Смерть защитника-не-игрока = ЕДИНОЕ правило тел (2026-09-11, аудит
  боя с животными):** IsFatalHit (Head/Heart ≥ 50 урона) ИЛИ реальное
  состояние тела после удара — жизненно важная часть уничтожена
  (`IBodyDataProvider.IsEntityAlive`: Head/Heart RedHP ≤ 0) ИЛИ полный
  дренаж HP → Victory/EndCombat. Раньше домены смерти (NPC/AnimalService)
  ждали «суммарный HP ≤ 0» — при per-part floor (урон в уже мёртвую часть
  теряется) сумма практически не обнуляется → сущности «бессмертны» в
  честном бою. Тот же фикс в NPCCombatAdapter/AnimalService.OnDamageApplied
  → NPCDeathEvent (труп/killfeed).
- **Животные — легитимные участники боя (2026-09-11):** Space-таргетинг
  игрока видит волка/оленя/кроля (NPC ∪ животные, IAnimalService); статы
  вида (SpeciesRegistry), Quadruped-морфология (таблица попаданий);
  месть — чейз + укус вплотную (кулдаун 2 тика < EnemyTurnTimeout);
  de-aggro → CombatDisengageEvent → AbandonCombat. См. ANIMALS.md §5.

#### 1.4.2. Стойка защиты игрока (R16)

Клавиша **G** циклирует стойку: `None → Dodge → Parry (WeaponMain) →
Shield (WeaponOff) → None` (`PlayerCombatAdapter.TickDefenseStance`,
анти-спам 0.3с). Публикуется `DefenseIntentEvent` → `CombatModule` →
`ICombatService.ExecuteDefense` — стойка применяется слоем §7 к СЛЕДУЮЩЕЙ
входящей атаке. Выбор работает и вне боя (подготовка). R21-2: «защита =
действие хода» удалена (ходов нет); стойка — реакция на следующую атаку
независимо от темпа. Shield-стойка доступна без WeaponOff при Ци ≥ 10
(см. §5, R21-4). Тост «🛡 Стойка: …» — GameWorldController.

## 2. 11-слойный конвейер прохождения урона

Любая атака (техника или обычный удар) проходит через **11 слоёв обработки**, прежде чем привести к фактическому урону HP части тела. Порядок слоёв строго фиксирован.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                  КОНВЕЙЕР ПРОХОЖДЕНИЯ УРОНА (11 СЛОЁВ)                       │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                               │
│  СЛОЙ 1 — ИСХОДНЫЙ УРОН (RAW DAMAGE)                                          │
│  ├── capacity = baseCapacity(type) × 2^(techniqueLevel-1) × (1 + mastery/100 × 0.5) │
│  ├── rawDamage = capacity × gradeMultiplier × ultimateMultiplier              │
│  ├── (+ бонус урона оружия для melee_weapon: bonusDamage = weaponDamage × statScaling) │
│  └── gradeMultiplier: common=1.0, refined=1.3, perfect=1.6, transcendent=2.0  │
│      ultimateMultiplier: isUltimate ? 2.0 : 1.0                               │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 2 — ПОДАВЛЕНИЕ УРОВНЕМ (LEVEL SUPPRESSION)                              │
│  ├── suppressionMult = getSuppression(attackerLevel, targetLevel, attackType) │
│  └── damage ×= suppressionMult                                                │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 3 — ОПРЕДЕЛЕНИЕ ЧАСТИ ТЕЛА (BODY PART ROLL)                             │
│  ├── hitPart = rollBodyPart(attacker, target, weapon)                         │
│  ├── head: 5%, torso: 40%, heart: 2%, arm: 20%, leg: 24%, hands: 8%, feet: 1% │
│  └── (+ бафф/дебафф активных формаций: damage ×= formationBuffMultiplier)     │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 4 — АКТИВНАЯ ЗАЩИТА (ACTIVE DEFENSE, выбор игрока)                      │
│  ├── Уклонение: dodgeChance = 5% + (AGI-10) × 0.5% - armorDodgePenalty        │
│  │   └── успех → damage = 0, END                                              │
│  ├── Парирование: parryChance = weaponParryBonus + (AGI-10) × 0.3%             │
│  │   └── успех → damage ×= (1 - blockEffectiveness), durability--             │
│  └── Блок щитом: blockChance = shieldBlock + (STR-10) × 0.2%                   │
│      └── успех → damage ×= (1 - shieldEffectiveness), shieldDurability--      │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 5 — БУФЕР ЦИ (QI BUFFER, для ЛЮБОГО урона)                              │
│  ├── Если currentQi > minQiForBuffer:                                         │
│  │   ├── Qi-техника + щит: 100% погл., 1:1, 0% пробитие                       │
│  │   ├── Qi-техника + сырая Ци: 90% погл., 3:1, 10% пробитие                  │
│  │   ├── Физ. урон + щит: 100% погл., 2:1, 0% пробитие                        │
│  │   └── Физ. урон + сырая Ци: 80% погл., 5:1, 20% пробитие                   │
│  └── Если Ци недостаточно → урон идёт дальше без поглощения                   │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 6 — БРОНЯ ЧАСТИ ТЕЛА: ПОКРЫТИЕ                                          │
│  ├── armor = getEquippedArmorForPart(hitPart)                                 │
│  └── if (random() < armor.coverage) → переход к СЛОЮ 7                        │
│      else → урон идёт напрямую в СЛОЙ 8 (минуя снижение брони)                │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 7 — СНИЖЕНИЕ УРОНА БРОНЁЙ                                              │
│  ├── Процентное снижение: damageReduction = min(0.8, armor.damageReduction    │
│  │                       + materialBonus + gradeBonus)  // кап 80%            │
│  ├── damage ×= (1 - damageReduction)                                          │
│  ├── Плоское вычитание (пробитие):                                            │
│  │   penetration = weapon.penetration + attackerSTR × 0.5 + techniquePenetration │
│  │   effectiveArmor = max(0, armor.armor - penetration)                       │
│  │   damage = max(1, damage - effectiveArmor × 0.5)                           │
│  └── Износ брони: armor.durability.current -= damage × 0.1 / hardness        │
│      (R21, 2026-09-20: СЛОИ 6-7 реализованы полностью: предметный            │
│       DamageReduction агрегируется в EquipmentDataProvider                    │
│       (GetDamageReductionPermil, ср. по броневым предметам) и ПОДКЛЮЧЕН     │
│       в DefenseContext.DamageReductionPermil поверх баффов/формаций;         │
│       плоское вычитание — в DefenseProcessor.ApplyDefense ПОСЛЕ процентного. │
│       Формула кривой брони — armor/(armor+100) в промилле.)                  │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 8 — МАТЕРИАЛ ТЕЛА ЦЕЛИ                                                  │
│  ├── materialReduction = getMaterialReduction(target.bodyMaterial)             │
│  └── damage ×= (1 - materialReduction)                                        │
│      (organic 0%, scaled 30%, chitin 20%, ethereal 70% физ., mineral 50%)    │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 9 — РАСПРЕДЕЛЕНИЕ ПО HP (одновременный split 0.7/0.3)                   │
│  ├── redHP   -= damage × 0.7   // 70% в функциональную HP                      │
│  ├── blackHP -= damage × 0.3   // 30% в структурную HP                         │
│  ├── При redHP ≤ 0 → паралич части тела                                       │
│  └── При blackHP ≤ 0 → отрубание части тела                                   │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 10 — ПОСЛЕДСТВИЯ (CONSEQUENCES)                                         │
│  ├── Кровотечение: если damage > threshold → bleedDamage per tick (1..10 HP)  │
│  ├── Шок: если redHP < 30% maxHP → штрафы к действиям                         │
│  ├── Оглушение: шанс = damage / maxHP × 10%                                   │
│  ├── Смерть: если heart HP ≤ 0 ИЛИ head HP ≤ 0                                │
│  └── DoT-эффекты стихий (burn, poison, freeze)                                │
│                                                                               │
│       ↓                                                                       │
│  СЛОЙ 11 — ЛУТ-ГЕНЕРАЦИЯ (ЗАПЛАНИРОВАН)                                       │
│  └── Генерация дропа на основе уровня, стихии, вида — будущая задача          │
│                                                                               │
└──────────────────────────────────────────────────────────────────────────────┘
```

> Слои 1–10 реализованы; слой 11 (loot generation) помечен как будущая задача. Под-опции (1b weapon bonus, 3b formation buff, 10b loot) входят в основные слои как под-этапы.

## 3. Авторитетная формула урона

```
finalDamage = capacity × gradeMultiplier × ultimateMultiplier
```

Где:
- `capacity = baseCapacity(type) × 2^(techniqueLevel-1) × (1 + mastery/100 × 0.5)`.
- `gradeMultiplier`: common=1.0, refined=1.3, perfect=1.6, transcendent=2.0.
- `ultimateMultiplier`: `isUltimate ? 2.0 : 1.0`.

> **Внимание:** Любые формулы, использующие `qiDensity × statMultiplier × masteryBonus` или `qiInvested` как базу, считаются устаревшими. Единственная правильная формула использует `capacity`.

### 3.1. Плотность Ци (qiDensity)

```
qiDensity = 2^(cultivationLevel - 1)
```

Геометрический рост ×2 за каждый уровень культивации. `qiDensity` встроена в формулу `capacity` как `2^(techniqueLevel-1)` и отдельно в расчёте урона не фигурирует.

## 4. Типы атак (5 подтипов)

Все атаки делятся на 2 группы (Melee и Ranged) и 5 подтипов. Каждый подтип имеет базовую ёмкость (`baseCapacity`), определяющую максимально обрабатываемое техникой Ци.

### 4.1. Ближний бой (Melee)

| Подтип | Описание | baseCapacity | Бонус STR | Бонус AGI |
|--------|----------|--------------|-----------|-----------|
| `melee_strike` | Удар телом (без оружия) | 64 | 5% | 2.5% |
| `melee_weapon` | Удар с оружием | 48 | 2.5% | 5% |

### 4.2. Дальний бой (Ranged)

| Подтип | Описание | baseCapacity | Бонус AGI | Бонус INT |
|--------|----------|--------------|-----------|-----------|
| `ranged_projectile` | Снаряд | 32 | 2.5% | 5% |
| `ranged_beam` | Луч | 32 | 2.5% | 5% |
| `ranged_aoe` | Область | 32 | 2.5% | 5% |

### 4.3. Бонус урона оружия (для melee_weapon)

Для атак с оружием поверх raw damage добавляется бонус:

```
baseDamage = max(handDamage, weaponDamage × 0.5)
bonusDamage = weaponDamage × statScaling
rawDamage += bonusDamage
```

См. `05_data/CONFIGURATIONS.md` и `06_player/EQUIPMENT_SYSTEM.md` для деталей.

### 4.4. Площадные техники — AoE «мгновенный залп» (R25, 2026-09-21)

> План: checkpoints/plans/2026-09-20_r23_multicombat_aoe_design.md §2.2-A
> (вариант A — выбор пользователя; B «живые зоны» — фаза 2). Решения
> пользователя 2026-09-21: friendly-fire — нейтралы ЗАДЕВАЮТСЯ («мир
> жесток», месть включается сама); эпицентр — точка прицеливания (курсор).

Подтип `ranged_aoe` + форма (`AoeShape` в TechniqueData, заполняет генератор):
**None** (обычная техника — все существующие), **Circle** («огненный шар»:
взрыв в эпицентре прицела, спад от эпицентра), **Cone** («волна пламени»:
от кастера в сторону прицела, halfAngle 30/45/60°), **Semicircle** («веер
Ци»: полукруг 90° перед кастером), **Line** («копьё Ци»: луч шириной ~1
тайл вдоль прицела).

- **Геометрия — int-математика тайлов (ЗАПРЕТ 3.9):** круг/полукруг —
  Чебышёв; конус — квадрат скалярного произведения (cos²30=3/4, cos²45=1/2,
  cos²60=1/4, cos²90=0 — рациональные дроби, сравнение квадратов без
  float/тригонометрии); линия — проекция + кросс-произведение. Реализация:
  `AoEResolver` (Modules/Combat, паттерн sanctioned-exceptions как
  CombatRangeGateService).
- **Прицел:** игрок — курсор мыши (милли-пиксели → тайл, int-деление;
  `AttackIntentEvent.AimTileX/Y`); NPC — позиция заявленной цели; фолбэк —
  позиция кастера. Aim переживает pending-каст (`PendingTechnique.AimTile`).
- **Мгновенный залп:** при резолве атака-техники AoE CombatService
  собирает цели (NPC ∪ звери ∪ игрок, кастер исключён; сортировка по
  близости к источнику спада; срез `AoeMaxTargets`) и прогоняет КАЖДУЮ
  цель через ПОЛНЫЙ 11-слойный пайплайн (`BuildAndExecuteDamageRequest`):
  броня/щит Ци/парирование/месть per-target честны для каждого задетого.
  `TechniqueUsedEvent` публикуется ОДИН раз на залп (кулдаун/мастерство
  начислены CompleteUse до интента, Ци списана тиками зарядки).
- **Спад силы:** `AoeFalloffPermil` (500‰ = ×0.5 на краю) — per-target
  множитель potency: `potency_target = potency_base × (1000 − falloff ×
  dist/radius) / 1000`. Источник спада: круг — эпицентр, конус/полукруг/
  линия — кастер. Заряженная мощь масштабируется честно (1500‰ × 0.7 =
  1050‰).
- **Friendly-fire — нейтралы задеваются** (решение пользователя): месть
  включается САМА (`DamageAppliedEvent → NPCAIService.RetaliateOrFlee`
  per-target). Конус сквозь деревню = толпа мстящих. Killfeed/цифры урона
  — уже per-target.
- **SpareAllies-хук** (§6.4 плана): `TechniqueData.SpareAlliesPermil` +
  `AoEResolver.AllyCheck` (null в v1 — сопартийцев нет). Появится party-
  система → «бережное Пламя» (D&D Careful Spell) включится без переделки.
- **Генерация:** 10% Combat-техник в `DetermineSubtype` → RangedAoe +
  форма из пула {Circle, Cone, Semicircle}; рецепты радиусов/спада —
  `ApplyAoeParams` (растут с уровнем). Тест-набор игрока: TechniqueGrantPhase
  выдаёт до 3 форм (конус/полукруг/круг) при свободной ёмкости библиотеки.
- **AoeImpactEvent** (форма/эпицентр/радиус/цели/стихия) — публикуется до
  per-target резолвов; VFX-фаза (R29+) рисует вспышки форм по нему.
  Сейв: поля AoE в TechniqueSnapshotDto (int, старые сейвы → None/0).
- QA: COMBAT_SIM 3h — (a) стенд геометрии форм, (b) конус игрока в толпу
  (per-target урон + AoeImpact ≥2 целей + месть «нейтралов»), (c) AoE-залп
  NPC (игрок задет + месть соседа на NPC-кастера).

## 5. Буфер Ци как защита

Ци защищает практика от ЛЮБОГО урона — даже во сне и даже если практик не использует активную защиту.

> **R21 (2026-09-20) — реализация пассивного режима.** Критерий «практика» в
> коде: текущее Ци ≥ 10 (MIN_QI_FOR_BUFFER). Уровень в доках не задан:
> практик = пробуждённое ядро (L1+) → Ци > 0; смертный L0 (Ци = 0) и
> опустошённый практик поглощения НЕ получают. Реализовано как дефолт:
> буфер игрока не активирован и Ци ≥ 10 → DamageService автоматически
> применяет режим **RawQi** (COMBAT_SYSTEM §5.1, физика 80%/5:1/20%);
> NPC — авто-активация RawQi в QiDataProvider.SetQiState (спаун/загрузка/
> реген). Активная Defense-техника (Z) / Barrier-формация по-прежнему
> переключает режим в **Shield** (100%/2:1/0%); G-стойка Shield доступна
> без физического предмета в WeaponOff (Qi-щит ≠ физический щит; до R21
> стойка была мёртвой — генератор не создаёт WeaponOff-предметов).

> **P1-12 (аудит 09.22, Фазы 9/10) — исключение: Чистый урон.**
> `DamageType.Pure` — абсолютный урон: Ци-буфер его НЕ поглощает и НЕ
> оплачивает (ветка буфера в DamageService пропускается целиком ДО
> `CalculateBufferAbsorption()` — ни `QiConsumeRequestEvent` игрока, ни
> `TryConsumeQi` NPC; поглощение 0, пробитие = полный урон после
> активной-защитной модификации). Раньше Qi списывалось «мимо» результата:
> урон формально проходил сквозь Ци, но ресурс тратился (runtime-пример:
> Pure 100 → absorbed=0, Ци игрока 1000→600). Броня/материал тела (§7,
> слои 6-8) к Pure применяются как обычно. Страж — QA-сим AUDIT0922
> секция K (игрок + NPC + контроль Physical).

| 2 | ×0.1 | ×0.25 | ×0.5 |
| 3 | ×0.0 | ×0.05 | ×0.25 |
| 4 | ×0.0 | ×0.0 | ×0.1 |
| 5+ | ×0.0 | ×0.0 | ×0.0 |

## 7. Система попадания

> **R16:** выбор активной защиты (слой 4): игрок — клавиша G (стойка,
> §1.4.2); NPC — `NPCDefenseSelector` (§1.4.1). Визуальная обратная связь
> удара — слэш-дуги/искры `StrikeFxRenderer` + замах оружия (R15-спрайты,
> sin-выпад 0.42с) — см. SPRITE_CATALOG §22.

### 7.1. Уклонение (Dodge)

```
dodgeChance = 5% + (AGI - 10) × 0.5% - armorDodgePenalty
```

При успехе → `damage = 0`, атака завершается.

### 7.2. Парирование (Parry)

**Требования:** имеется оружие или щит, цель в пределах досягаемости.

```
parryChance = weaponParryBonus + (AGI - 10) × 0.3%
```

При успехе → `damage ×= (1 - blockEffectiveness)`, прочность оружия снижается.

### 7.3. Блок щитом (Block)

```
blockChance = shieldBlock + (STR - 10) × 0.2%
```

При успехе → `damage ×= (1 - shieldEffectiveness)`, прочность щита снижается.

### 8.2. Скорость атаки: модель готовности (R21-2, 2026-09-20)

```
// Готовность удара (readiness, промилле; ЗАПРЕТ 3.9 — int):
readiness += attackSpeedPermil × deltaTime   // каждый тик (1 тик = 1с, WorldService.DeltaTime=1)
удар принимается при readiness ≥ 1000‰ (AttackThresholdPermil) и вычитает порог

// Скорость атаки:
attackSpeedPermil = WeaponMain.AttackSpeedPermil × (1000 + AGI × 10) / 1000
//   оружие: AttackSpeedFactor класса × 1000 (генератор пишет на предмет):
//   кинжал 1300, меч 1000, копьё 900, топор 1000, двуруч 750, посох 1000, лук 800
//   без оружия (кулаки) = 1000; звери (не в провайдере экипировки) = 500 (видовой темп,
//   1 атака / 2 тика — прежний каденс волка)
// AGI-фактор = 1 + AGI×0.01 — инверсия прежней формулы длительности §8.2
```

> **Пример (Normal, 1 тик = 1с):** волк 500‰/тик → укус раз в 2 тика;
> игрок с мечом (1000 × 1.1 AGI=10) → 1.1 удара/тик → **2.2 удара за укус
> волка**; кинжал 1430 → 2.86; двуруч 825 → 0.93 (реже волка, но больнее —
> урон-компенсация SpeedDamageScale была с самого начала). Ровно
> запрошенный эффект («пока волк укусит раз — я стукну два»).
>
> Кулдауны адаптеров удалены (кулдаун 1.6с NPC, волчьи 2 тика, 1с игрока) —
> единый источник темпа: CombatService.AccrueReadiness. Адаптер игрока
> хранит только ОЦЕНКУ каденции (анти-спам/HUD; истина — readiness-гейт).
> Время каста техник — по-прежнему проводимость меридиан (ALGORITHMS §12);
> заряженные техники (fill-модель) готовность не расходуют дополнительно —
> их темп = зарядка + Ци. StatBonus "attackSpeed" и StatType.AttackSpeed
> (софт-капы) — подготовлено, но пока НЕ подключено к множителю (будущая фаза).
>
> **R23-1 (аудит CMB-1, 2026-09-20):** контракт выше теперь честный в коде:
> charged-атака (`isCharged ∨ potency > 1000‰`) гейт готовности ПРОПУСКАЕТ
> и readiness не списывает (зарядка TechniqueChargeService была замахом;
> прежде гейт отбрасывал выпуск — игрок терял Ци+кулдаун+мастерство без
> эффекта). Если выпуск всё же отклонён иными гейтами («не участник» /
> «каст уже идёт») — `PlayerTechniqueCaster.OnAttackRejected` возвращает
> кулдаун и мастерство (`TechniqueService.RefundUse`, окно 2с); Ци НЕ
> возвращается — энергия рассеялась (лор: списана тиками зарядки).
> QA: COMBAT_SIM 3e (b)-(d) — гард «charged при 600‰ = Accepted, readiness
> не меняется».

## 11. Специальные механики

### 11.1. DoT (Damage-over-Time)

- **Burn (горение):** 5% от исходного урона за тик в течение 3 тиков.
- **Bleed (кровотечение):** 1–10 HP/тик в зависимости от уровня (5 уровней).
- **Poison (отравление):** прогрессирует по стадиям (onset → progression → critical), зависит от Grade техники яда.

### 11.2. AoE (Area of Effect)

- Формации (магические массивы) создают AoE-зоны размером от **3×3 м** (Small) до **300×300 м** (Heavy).
- Эффект формации действует в радиусе 50 м – 5 км.
- `ranged_aoe` техники создают AoE через эффекты `ExpandingEffect` (см. `02_systems/TECHNIQUE_EFFECTS.md`).

### 11.3. Chain Lightning

Молниевые техники (`lightning`) при попадании по цели наносят **50% урона по 2 соседним целям**. Transcendent-версия: `+25% урона каждой следующей цели` (chain_scaling).

### 11.4. Knockback (отброс)

Воздушные техники (`air`) отбрасывают цель на **3 клетки**. Не зависит от размера цели (но цели `Huge+` иммунны).

### 11.5. Pierce (пробитие)

- Пустота (`void`): +30% пробития брони.
- Transcendent Нейтральный: +10% пробития брони (`armor_pierce`).
- Пробитие оружия: `weapon.penetration + attackerSTR × 0.5 + techniquePenetration`.

## 12. Применение урона к телу (split 0.7/0.3)

Урон распределяется **одновременно** (не последовательно!):

```
redHP   -= damage × 0.7     // 70% в функциональную HP
blackHP -= damage × 0.3     // 30% в структурную HP
```

- При `redHP ≤ 0` → паралич части тела (Crippled).
- При `blackHP ≤ 0` → отрубание части тела (Severed).
- При `heart HP ≤ 0` или `head HP ≤ 0` → смерть.

> См. `02_systems/BODY_SYSTEM.md` §5 для деталей о двойной HP.

## 13. Пример полного расчёта

**Сценарий:**
- Атакующий: L3, Combat-Melee L2, Refined, Mastery 50%.
- Защищающийся: L4, Qi 5000, защита Raw Qi.

**Расчёт:**

```
1. baseCapacity (melee_strike) = 64
2. qiCost = 64 × 2^1 = 128

3. capacity = 64 × 2^1 × (1 + 50 × 0.005)
            = 64 × 2 × 1.25
            = 160

4. rawDamage = 160 × 1.3 (Refined)
             = 208

5. Level Suppression:
   diff = 4 - 3 = 1
   multiplier = 0.75 (Technique)
   damage = 208 × 0.75 = 156

6. Qi Buffer (Qi-техника vs Raw Qi):
   absorbed = 156 × 0.9 = 140.4
   qiNeeded = 140.4 × 3 = 421.2
   piercing = 156 × 0.1 = 15.6

7. (Пропускаем СЛОИ 6–8 — допустим, без брони и материала)
8. Final damage = 15.6
9. redHP   -= 15.6 × 0.7 = 10.92
10. blackHP -= 15.6 × 0.3 = 4.68
```

## 14. Структура данных боя

Боевая логика выполняется в **pure-C# модулях** (без зависимости от движка). Примерная структура данных:

```
DamageInfo:
  amount:        int            // итоговый урон (после всех слоёв)
  element:       Element        // стихия
  source:        EntityId       // атакующий
  hitPart:       BodyPartId     // поражённая часть тела
  hitPoint:      Position2D     // точка попадания
  isCritical:    bool
  isUltimate:    bool

DamageResult:
  rawDamage:          int       // после СЛОЯ 1
  postSuppression:    int       // после СЛОЯ 2
  postQiBuffer:       int       // после СЛОЯ 5
  postArmor:          int       // после СЛОЯ 7
  postMaterial:       int       // после СЛОЯ 8
  redHPDamage:        int       // 70%
  blackHPDamage:      int       // 30%
  isFatal:            bool      // смерть
  consequences:       List<Consequence>  // bleed, stun, shock
```

> События боя публикуются через шину событий как `readonly struct` (zero-GC). См. `01_architecture/DI_AND_EVENTBUS.md`.

## 15. Производительность

- Battle tick обрабатывается в одном проходе по всем активным участникам боя.
- При `MaxActiveNPCs = 100` и типичном бое 10×10: ~5 ms на полный battle tick.
- Pooling объектов `DamageInfo`/`DamageResult` — обязателен (zero-GC policy).
- Слои 1–8 выполняются синхронно в одном вызове; слои 9–10 могут эмитить события для других систем (анимация, звук, UI).

## Детерминированность (Q5)

Все случайности в бою используют `ICombatRng` (обёртка над `SeededRandom`, seed=12345). Это обеспечивает:
- **Воспроизводимость боёв** — одинаковый seed → одинаковый результат (полезно для отладки и тестов).
- **Корректную работу с save/load** в будущем — состояние генератора сериализуется, бой продолжается детерминированно после загрузки.
- **Удобство тестирования** — фиксированный seed даёт стабильные кейсы в unit-тестах.

### Принцип
- `ICombatRng` — интерфейс с методами `Next(int)`, `NextFloat()`, `NextBool(double)`.
- `CombatRng` — реализация-обёртка над `SeededRandom` (seed=12345 по умолчанию).
- НЕ использует `Random.Shared` или `System.Random()` (недетерминированно).

### Где внедряется
`ICombatRng` инжектится через DI в следующие сервисы:
- `CombatService` — основной оркестратор боя (выбор цели, ход).
- `DamageService` — расчёт урона, криты, проки эффектов.
- `ElementalEffectService` — шанс наложения стихийных эффектов (burn, slow, stun, chain...).
- `CombatConsequencesService` — кровотечение, оглушение, шок (слой 10).

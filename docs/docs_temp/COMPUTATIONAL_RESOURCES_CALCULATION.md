## 🏗️ Архитектура локации (модульная)

### Иерархия хранения

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    ИЕРАРХИЯ ДАННЫХ ЛОКАЦИИ                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│   УРОВЕНЬ 1: МЕТАДАННЫЕ ЛОКАЦИИ                                             │
│   ├── locationId: string                                                    │
│   ├── name: string                                                          │
│   ├── worldX, worldY: int (позиция на карте мира)                          │
│   ├── width, height: int (в метрах, ПЕРЕМЕННЫЕ!)                           │
│   ├── terrainType: enum                                                     │
│   ├── qiDensity: int                                                        │
│   └── climate: enum                                                         │
│   Размер: ~1 KB                                                             │
│                                                                              │
│   УРОВЕНЬ 2: ТАЙЛОВАЯ СЕТКА (сжатая)                                        │
│   ├── TileMapService управляет загрузкой/выгрузкой чанков                   │
│   ├── Сжатие: RLE для одинаковых тайлов                                    │
│   └── Сжатие: Sparse Array для пустых тайлов                               │
│   Размер: зависит от типа локации                                          │
│                                                                              │
│   УРОВЕНЬ 3: ОБЪЕКТЫ (динамические)                                         │
│   ├── DestructibleService — разрушаемые объекты                             │
│   ├── ResourceService — ресурсы                                             │
│   └── Размер: пропорционален количеству объектов                           │
│                                                                              │
│   УРОВЕНЬ 4: СУБЪЕКТЫ (динамические)                                        │
│   ├── NPCService — Dictionary<string, NPCState>                            │
│   ├── NPCSpawnerService — генерация и размещение                           │
│   └── Размер: пропорционален количеству NPC/монстров                       │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### Модульная архитектура: влияние на ресурсы

| Модуль | Влияние на CPU | Влияние на память | Влияние на MessagePipe |
|--------|----------------|-------------------|----------------------|
| **Tile** | Генерация тайлов, Pathfinding | TileMapData (основной потребитель) | TileChangedEvent (редко) |
| **NPC** | AI-тик (NPCAIService), движение | NPCState × N (BodyParts, Inventory) | QiChangedEvent → кэш для AI |
| **Body** | BodyDamageCalculator, BodyEnhancementSystem | BodyPart × 11 × N | BodyPartDamagedEvent |
| **Qi** | QiRegenCalculator (тик регена), QiBufferService | QiState × N | QiChangedEvent (часто!) |
| **Combat** | DamageCalculator, DefenseProcessor, LevelSuppression | Временные структуры | CombatEvent (при бое) |
| **Formation** | FormationCalculator, FormationQiPool | FormationState × M | FormationDrainEvent |
| **Charger** | ChargerService, ChargerHeat | ChargerState × K | ChargerHeatEvent |
| **Buff** | BuffTickProcessor (тик баффов) | ActiveBuff × L | BuffExpiredEvent |
| **Save** | SaveDataAggregator, сериализация | SaveSlotData | SaveRequestedEvent |
| **Player** | PlayerInputService, PlayerCombatAdapter | PlayerData (1 экземпляр) | PlayerMovedEvent |
| **Generator** | TechniqueGeneratorService, ItemGeneratorService | TechniqueRegistry, ItemDatabase | — (вызов при генерации) |
| **World** | TimeService (тик), EventService, FactionService | WorldState, LocationData | TimeHourChanged, DayChanged |
| **Inventory** | EquipmentService, CraftingService | InventorySlot × P | InventoryChangedEvent |

## 🧮 Расчёт памяти NPC (модульная архитектура)

### NPCState — основной потребитель памяти для NPC

```
NPCState (один экземпляр):
├── Идентификация: ~200 bytes (strings, enums)
├── SoulData: ~100 bytes (long CoreCapacity, float Conductivity, etc.)
├── BodyParts: 11 × BodyPart ≈ 11 × 64 bytes = 704 bytes
├── EquipmentIds: 7 × KeyValuePair ≈ 200 bytes
├── TechniqueIds: 1-4 × string ≈ 200 bytes
├── InventorySlots: 2-5 × InventorySlot ≈ 300 bytes
├── Threats: Dictionary (обычно пустой) ≈ 50 bytes
├── Прочее: ~200 bytes
└── Итого: ~1.9 KB на NPC
```

### Расчёт по размеру локации

## ⚡ Расчёт производительности (модульная архитектура)

### CPU: Основные циклы

| Операция | Модуль | Сложность | При 100 NPC |
|----------|--------|-----------|-------------|
| AI-тик | NPCAIService | O(N) | ~2 ms |
| Qi-реген | QiRegenCalculator | O(N) | ~0.5 ms |
| Buff-тик | BuffTickProcessor | O(N × B) | ~1 ms |
| Движение NPC | NPCMovementService | O(N) | ~1 ms |
| Обновление тайлов | TileMapService | O(changed) | ~0.1 ms |
| Pathfinding (A*) | TileMapService | O(n log n) | ~5-50 ms |
| Проверка столкновений | Physics2D | O(N²) worst | ~0.5 ms |
| Сериализация | SaveService | O(N) | ~5 ms |

### CPU: MessagePipe — накладные расходы

| Событие | Частота | Подписчики | Накладные расходы |
|---------|---------|------------|-------------------|
| QiChangedEvent | При каждом изменении Ци | NPCService (кэш) | ~0.01 ms/event |
| TimeHourChanged | Раз в игровой час | WorldService, NPCService | ~0.01 ms/event |
| NPCAIStateChanged | При смене состояния | UI | ~0.01 ms/event |
| DamageDealtEvent | При каждом ударе | UI, Achievement(TBD) | ~0.02 ms/event |

> **Вывод:** MessagePipe (readonly struct) — минимальные накладные расходы. Zero GC allocation.
> Для 100 NPC с 10 событиями/сек = ~0.1 ms/сек — пренебрежимо мало.

|----------|----------|
| Спрайты на экран | ~1000-5000 |
| Draw calls | ~50-200 |
| Видеопамять | ~100-500 MB |

## 🏗️ Оптимизации модульной архитектуры

### 1. Per-entity DataProvider Pattern

Вместо инъекции IQiService / IBodyService в каждый модуль:
- `QiDataProvider` — кэш Qi-состояний по EntityId
- `BodyDataProvider` — кэш BodyParts по EntityId
- `EquipmentDataProvider` — кэш Equipment по EntityId

```
+ Преимущества:
  - Модули не знают друг о друге (Hub-and-Spoke)
  - O(1) доступ к данным
  - Кэш обновляется через MessagePipe-события
- Затраты:
  - Дополнительная память: ~2-4 KB на NPC (3 провайдера)
  - Синхронизация кэша: ~0.05 ms на NPC при обновлении
```

### 2. Чанковая загрузка локаций

```
Локация 10×10 км (25M тайлов):
Чанк = 200×200 м = 100×100 тайлов = 10,000 тайлов
Чанков в локации: 50×50 = 2,500 чанков

Радиус загрузки = 3 чанка (600×600 м):
Загружено чанков: 7×7 = 49 чанков
Загружено тайлов: 49 × 10,000 = 490,000 тайлов
Память: ~15 MB (сжатый) вместо 150 MB (полная локация)
```

### 3. Сжатие данных

| Метод | Коэффициент | Когда использовать |
|-------|-------------|-------------------|
| RLE | 10-20× | Дикая местность (большие области одинаковых тайлов) |
| Sparse Array | 3-10× | Города с пустыми зонами |
| Чанковая загрузка | 50× | Локации >1 км |
| LOD для тайлов | 2-5× | Дальние тайлы (только тип) |

### 4. AI-оптимизация

| Оптимизация | Описание | Экономия |
|-------------|----------|----------|
| AI-тик по расписанию | Не все NPC обновляются каждый кадр | 50-80% CPU |
| Радиус активации | NPC далеко от игрока не обновляют AI | 60-90% CPU |
| Кэширование решений | NPC повторяет решение N тиков | 30-50% CPU |
| Пул объектов | Переиспользование NPCState при смерти/респавне | GC reduction |

## 📈 Итоговая оценка

### Можно ли запустить игру на ПК?

| Сценарий | Ответ | Примечание |
|----------|-------|------------|
| Малые локации (до 1 км) | ✅ Да | Любой современный ПК |
| Средние локации (1-3 км) | ✅ Да | С чанковой загрузкой |
| Большие локации (3-10 км) | ✅ Да | Требует оптимизаций |
| Мегаполис 10×10 км | ⚠️ С ограничениями | Только с чанковой загрузкой |

### Рекомендуемые спецификации ПК

| Сценарий | CPU | RAM | GPU |
|----------|-----|-----|-----|
| Минимальные | 4 ядра, 2.5 GHz | 8 GB | GTX 1050 |
| Рекомендуемые | 6+ ядер, 3.0 GHz | 16 GB | GTX 1660 |
| Мегаполис 10×10 км | 8+ ядер, 3.5 GHz | 32 GB | RTX 3060 |

### Ключевые оптимизации (по приоритету)

1. **Чанковая загрузка** — обязательна для локаций >1 км
2. **AI-тик по расписанию** — снижение CPU на 50-80%
3. **Per-entity кэш** — O(1) доступ к данным (уже реализовано)
4. **Сжатие RLE** — для дикой местности
5. **Пул объектов** — для частых созданий/удалений NPC

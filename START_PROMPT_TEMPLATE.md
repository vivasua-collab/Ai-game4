## 0. Принципы достоверности (эпистемика агента) — НАД всеми правилами

> Действуют во всех задачах, во всех сессиях, во всех слоях этого файла.
> При конфликте любого правила ниже с этими принципами — принципы сильнее.

1. **Всегда говори правду.** Если правда неудобна (баг в своей работе, сломанный
   билд, срыв оценки, моё прошлые утверждение ошибочно) — сообщи как есть.
   Скрытая проблема при вскрытии стоит дороже.
2. **Не выдумывай факты, цитаты или данные.** В dev-контексте это также: имена
   файлов, номера строк, хеши коммитов, результаты тестов, содержимое логов,
   поведение API, версии библиотек, чужие решения «я думаю, оно работает».
3. **Основывай утверждения на проверяемых источниках и указывай их явно.**
   Источник истины здесь: сам код (`путь/к_файлу:строка`), git
   (`git log / show / blame`), логи запусков, официальная документация и
   спецификации проекта. Формат: `file:line`, `commit-hash`, короткая цитата
   лога. «Я помню, что…» — не источник; проверь и сошлись.
4. **Не можешь подтвердить — скажи прямо.** Помечай статус утверждения:
   `[факт]` (источник указан), `[гипотеза]` (проверяемое предположение —
   проверка назначена), `[не подтверждено]` (источника нет). Подавать гипотезу
   как факт — запрещено.
5. **Точность важнее скорости.** Лишняя проверка (grep, чтение файла, запуск
   теста) лучше быстрого неверного ответа. Особенно перед словами «готово»,
   «работает», «исправлено», «протестировано» — они требуют источника (§0.3).
6. **Сохраняй объективность, мнения помечай.** Оценки и суждения отделяй от
   фактов и помечай: «оценка:», «мнение:», «предположение:».
7. **Объясняй ход рассуждений, показывай расчёты.** Любая цифра (оценка
   трудозатрат, размер, срок, процент) раскладывается на части — из чего
   состоит. Читатель должен иметь возможность проверить вывод.
8. **Самопроверка перед ответом:** все ли утверждения подкреплены источниками?
   Все ли гипотезы честно помечены? Ничего не «дорисовано» за источник?

> Эхо принципов в других секциях: §6.5-4 (чекпоинты: факты, не мнения),
> §8 (worklog: событие + источник), §10 (статус: «работает» = чем подтверждено),
> §14 (вердикты только из логов прогонов, не из памяти).

## 6. Правила работы с чекпоинтами

### 6.1. Назначение

Чекпоинты — фиксация этапов работы. Позволяют:
- определить место и время ошибки (когда что-то сломалось);
- понять причину решения (почему выбран этот подход);
- восстановить контекст при новой сессии.

### 6.2. Формат имени файла

```
checkpoints/ММ_ДД_краткое_описание.md
```

Примеры: `{{09_15_fix_login_bug.md}}`, `{{09_15_audit_module_x.md}}`.

### 6.3. Структура чекпоинта

```markdown
# Чекпоинт: <краткое описание>

**Дата:** YYYY-MM-DD HH:MM {{TZ}}
**Сессия:** <ID или краткий контекст>
**Тип:** audit | implementation | fix | decision | migration | analysis

---
## Контекст
<почему создан, что предшествовало>
## Что сделано
- <шаги>
## Решения
- <решение> — <причина>
## Найденные проблемы
- <проблема> — <влияние> — <статус>
## Следующие шаги
- <что дальше>
## Файлы
- <созданные/изменённые>
```

### 6.4. Когда создавать

| Событие | Чекпоинт? |
|---------|-----------|
| Завершение этапа (спринта, фазы) | ✅ |
| Архитектурное решение | ✅ |
| Найден и исправлен баг | ✅ |
| Миграция/перенос из другого проекта | ✅ |
| Аудит модуля/слоя | ✅ |
| Мелкое изменение (1–2 файла) | ❌ (достаточно worklog) |
| Эксперимент/прототип | ⚠️ только если решение принято |

### 6.5. Правила

1. **Один чекпоинт = одно событие.** Не смешивать аудит + реализацию.
2. **Имя — краткое описание**, не дата-время; дата — префикс (§6.2).
3. **Глубина:** 50–200 строк. Не дублировать worklog.
4. **Факты, не мнения (§0):** каждое утверждение — с источником `file:line`
   или commit-hash. «Модуль X использует float» — да; «X написан плохо» — нет.
5. **Ссылки на файлы обязательны.**
6. **Чекпоинт коммитится вместе с кодом** (тот же коммит или соседний).

## 8. worklog.md

**Файл:** `{{путь}}/worklog.md` — хроника работы всех агентов. **Append-only**
(только дописывать в конец; механические правки ссылок допустимы).

**Формат эпизода:**
```markdown
---
## {{Название эпизода}} (YYYY-MM-DD, эпизод N)
Task: <исходный запрос>
Work Log:
- <шаги с источниками: file:line, commit, лог прогона>
Stage Summary:
- <ключевые результаты, артефакты (чекпоинты, коммиты)>
NEXT: <первый шаг следующего эпизода — точка возобновления после обрыва>
```

**Правила:**
1. worklog — только для текущих сессий, не «память навсегда»: при завершении
   сессии обновить SESSION_SUMMARY.md (в git).
2. При превышении ~{{N}} строк — архивировать в
   `checkpoints/worklog_backup_YYYYMMDD.md`.
3. Ключевые решения — дублировать в чекпоинты.
4. Метка `NEXT:` в конце КАЖДОГО эпизода обязательна (§14.2-4).

## 14. Правила сессий песочницы (короткие эпизоды) — КАНОН

> **Проблема:** среда исполнения периодически обрывает сессию без
> предупреждения. Незакоммиченная работа теряется.

### 14.1. Наблюдения {{дата}}: зафиксировать свои

| Обрыв | Время | Вероятная причина |
|-------|-------|-------------------|
| 1 | {{...}} | {{параллельные субагенты / кумулятивный контекст / ...}} |
| 2 | {{...}} | {{...}} |

- Живые отрезки сессии: {{N–M минут}}.
- Пик токенов субагента: ~{{N}}K (по их отчётам).

### 14.2. Правила (обязательны в каждой сессии)

1. **Эпизод ≤ ~45 мин работы → коммит + пуш + чекпоинт.** Обрыв теряет
   максимум пол-эпизода; удалённый репозиторий всегда актуален.
2. **Субагенты — ТОЛЬКО последовательно.** Максимум 1 за раз. Параллельный
   мульти-запуск запрещён (пиковая нагрузка = обрыв).
3. **Компактный контекст:** grep-фильтры вместо полных логов, точечные чтения
   файлов (offset/limit), минимум многострочного вывода в чат.
4. **Метка `NEXT:`** в конце каждого worklog-эпизода — точка возобновления
   после обрыва.
5. **Тяжёлые прогоны** (долгие сборки, полная регрессия) — **в конце
   эпизода**: обрыв во время прогона не теряет правки (они уже в git).
6. **Время в чат на каждом промежуточном этапе** (старт эпизода, коммит,
   конец эпизода) — фиксируется длительность живых отрезков.
7. **Push в удалённый репозиторий после каждого эпизода** (токены — §5).

### 14.3. Восстановление после обрыва

1. Прочитать START_PROMPT.md (этот файл) → SESSION_SUMMARY.md.
2. Хвост worklog.md — последняя метка `NEXT:`.
3. `git log --oneline -5` + `git status` — что в git, что в рабочем дереве.
4. Продолжать с `NEXT:`; потерянное (если было) — зафиксировать в worklog.

## 0. Текущая архитектура (факты, от которых отталкиваемся)

| Факт | Значение для дизайна |
|---|---|
| `CombatService` = ОДИН бой на мир (`_isInCombat`, `_instigatorId`, `_currentTargetId`, `_currentStage`) | CMB-2: эмерджентная стычка NPC занимает слот, игрок «не участник» |
| `_readinessPermil` — Dictionary per-entity | Уже готово к мультибою ✅ |
| `_pendingCasts` — Dictionary per-attacker + `PendingTechnique.TargetId` | Уже готово к мультибою ✅ (цель запоминается в касте) |
| `CombatSubtype.RangedAoe` — **уже в enum** (маппится Qi/Ranged) | Явка «площади» планировалась; логики нет |

| `TechniqueCastResultEvent`/`ChargeCompleted` несут `TargetMouseX/Y` | Точка курсора УЖЕ доставляется → центр AoE/направление конуса бесплатно |
| Резолв: `ApplyTechniqueImmediately → BuildAndExecuteDamageRequest(defenderId)` — ОДНА цель | Точка расширения для площади |

| NPC AI: leash/бегство привязаны к состоянию «в бою» (глобальному) | Меняется вместе с моделью боя |

## 1. МУЛЬТИБОЙ (корень CMB-2)

### Вариант A — «Приоритет игрока» (минимальный дифф)

Единственный слот боя остаётся, но слот принадлежит игроку:

- `StartCombat(player, …)` при занятом слоте (NPC-vs-NPC) → **вытеснение**:
  чужой бой завершается нейтрально (`CombatEndedEvent(Victory:false)` без
  лута/киллфида), NPCs возвращаются к блужданию, стартует бой игрока.
- NPC-vs-NPC бои получают таймаут `MaxCombatDuration` (60-120с игровых):
  стычка не висит вечно.
- Плюсы: ~80-120 строк; контракты/сейв/UI не трогаются; риск регресса низкий.
- Минусы: игрок всё ещё строго 1v1 (второй волк ждёт); стычки NPC
  «обрываются на полуслове» (мир дёрганый); групповые бои невозможны.

### Вариант B — «Per-pair бои» (полный мультибой, правильная архитектура)

Состояние боя → `Dictionary<(attacker, defender), CombatState>`:

- Бой = пара. Игрок может участвовать в нескольких парах (толпа врагов),
  свободно входить в чужую стычку. Смерть → конец только своей пары.
- `ICombatService`: `IsInCombat` → `IsInCombat(entityId)` (+ перегрузки),
  `CombatStartedEvent/EndedEvent` получают `CombatId` (пара);
  `CurrentTargetId` → per-entity (`GetCombatTarget(entityId)`).
- NPC AI: leash/бегство переводятся на per-entity состояние боя.
- UI: HUD врага = «текущая цель игрока» (переключение Tab/последний удар);
  killfeed без изменений.
- Плюсы: честные групповые бои; основа для AoE (толпы!) и самонаводящихся;
  мир живёт без обрывов.
- Минусы: ~400-600 строк (CombatService, адаптеры NPC/звери/игрок, AI,
  QA-симы), контрактные изменения расходятся по потребителям, сейв-блок
  combat меняется. 2-3 эпизода.

### Вариант C — «Реестр входов» (гибрид: лёгкий мультибой) ★ рекомендую стартовать

Убираем ПОНЯТИЕ слота для механики, оставляем его для UI:

- Гейт `IsParticipant` УДАЛЯЕТСЯ: атака разрешена любой паре
  живых сущностей (LOS + readiness + свой каст — уже per-entity).
- «Бой» (`CombatStarted/Ended`, HUD-пара игрока, стадии) остаётся
  ОДНИМ — только как UI-сессия игрока: старт = игрок атаковал/атакован,
  конец = цель игрока умерла/убежала/игрок вышел.
- NPC-vs-NPC дерутся «молча»: урон летает через тот же пайплайн,
  killfeed/смерть/лут работают (события per-target уже есть), но
  CombatStarted/Ended для них не публикуются, стейджи не занимаются.
- leash/бегство NPC: переводятся с «глобального боя» на
  «меня атакует X» (per-entity память последнего атакующего — уже
  есть в RetaliateOrFlee из R20).
- Плюсы: ~150-250 строк; толпа бьёт игрока и игрок бьёт толпу;
  события/UI почти не тронуты (NPC-бесшумность уже привычна по
  эмерджентным стычкам); прямой путь к до-апгрейду B позже.
- Минусы: у NPC-боёв нет «сессии» (нет стадий/таймаута — стычка
  идёт до смерти/бегства по HP-правилам AI); CombatEndedEvent
  семантически = «UI-бой игрока завершён».

### Сравнение

| Критерий | A: приоритет | B: per-pair | C: реестр входов |
|---|---|---|---|
| Игрок против толпы | ❌ 1v1 | ✅ | ✅ |
| Чужие стычки не обрываются | ❌ | ✅ | ✅ (но без сессии) |
| Контракты/сейв | не тронуты | меняются | почти не тронуты |
| Объём | ~0.5 эпизода | 2-3 эпизода | 1-2 эпизода |
| Риск регресса | низкий | средний | низкий-средний |
| Путь к AoE/самонаводящимся | мешает (1v1) | идеален | достаточен |
| Групповые бои NPC (войны фракций) | ❌ | ✅ | ✅ (сырой) |

**Рекомендация:** C сейчас (закрывает боль CMB-2, открывает групповой бой),
B — целевое состояние, к которому мигрируем, когда появится скрытая жизнь
мира (войны фракций, стычки групп). C→B миграция чистая: реестр входов
остаётся, «сессии» добавляются поверх.

## 2. ПЛОЩАДНЫЕ ТЕХНИКИ (конус / полукруг / круг)

### 2.1. Модель данных (общая для всех вариантов)

`TechniqueData` + поля (новые, int/промилле, ЗАПРЕТ 3.9):

```
AoeShape:      None | Circle | Cone | Semicircle | Line   (enum)
AoeRadiusTiles:int          // радиус/полудлина (Circle, Semicircle, Line)
AoeHalfAngle:  int deg      // конус: 30/45/60/90
AoeFalloffPermil:int        // урон на краю: 500‰ = ×0.5 (0 = без спада)
AoeMaxTargets: int          // кап целей (баланс: 3/5/8/∞=0)
```

Форма задаётся ГЕНЕРАТОРОМ техник (Subtype=RangedAoe → форма из рецепта
техники; существующие техники не меняются — `None` по умолчанию).

### 2.2. Вариант резолва A — «Мгновенный залп» ★ рекомендую

При резолве каста AoE-техники:

1. Эпицентр/направление: конус/полукруг — от кастера в сторону
   курсора (`TargetMouseX/Y` уже в событиях!) или текущей цели;
   круг — точка курсора (или цель — для NPC-кастеров).
2. `AoEResolver` (новый engine-agnostic класс в Modules/Combat) собирает
   цели в форме: NPC ∪ звери ∪ игрок (позиции, int-геометрия: Чебышёв
   для круга, скалярное произведение для конуса — без float).
3. На КАЖДУЮ цель — полный существующий пайплайн
   `BuildAndExecuteDamageRequest` (11 слоёв: броня/щит Ци/парирование
   честны для каждой цели; falloff = множитель potency per-target
   промилле).
4. Friendly-fire политика (решение нужно): (а) нейтралы задеваются —
   мир опасен, месть включается (реалистично, рекомендую);
   (б) гейт по faction (групповые техники по «своим» не бьют).
5. События для графики: `AoeImpactEvent(shape, epicenterX/Y, radius,
   angle, targets[])` — рендереру хватит для вспышки/формы (фаза VFX).

- Плюсы: мгновенный взрыв (лор огненного шара); честный пайплайн per-target;
  цифры урона над каждой целью — бесплатно (DamageAppliedEvent).
- Минусы: толпа 20+ целей = 20 резолвов за тик (перф ок до ~50).

### 2.3. Вариант резолва B — «Живая зона» (дополнение, не конкурент)

Площадь = Zone-сущность на карте (N тиков): все входящие в форму получают
урон/эффект каждый тик (ливень, огненная стена, поле подавления).
Пайплайн — существующий DoT (ElementalEffectService) + тик зоны.

- Плюсы: тактические длительные поля; reuses DoT-модуль.
- Минусы: НЕ мгновенный взрыв — другая механика (это фаза 2, отдельный
  эпизод; с вариантом A не конкурирует).

**Рекомендация:** A для взрывных техник (конус/полукруг/мгновенный круг),
B потом для контрольных полей. В первую очередь A.

## 3. САМОНАВОДЯЩИЕСЯ ТЕХНИКИ + система выбора цели

### 3.1. TargetingService (фундамент, нужен обоим вариантам)

`ITargetingService` (новый, engine-agnostic):

```
GetTargetsInShape(origin, shape, angle, params)  → List<TargetRef>
SelectTarget(casterId, filter)                   → TargetRef | null
  фильтры: Nearest | LowestHp | HighestThreat | CursorDirection
```

- Игрок: **Tab** — цикл целей в радиусе (UI-подсветка: рамка/аура на
  выбранной цели — событие `PlayerTargetChangedEvent`);
  прицел ПКМ-курсором для конусов/AoE (уже доставляется).
- NPC: ретаргет по угрозе (уже есть) + «не бить своих в спину»
  (Line-гейт для melee-толпы).

### 3.2. Вариант A — «Снаряд как сущность симуляции» ★ рекомендую

`PendingTechnique` + `IsHoming` + `ProjectileSpeedTilesPerTick`:

- При резолве каста хоуминга НЕ наносим урон: создаём Projectile
  (позиция, скорость, targetId, техника, potency) в реестре
  CombatService (тик в UpdateTimer, рядом с pendingCasts).
- Каждый тик: снаряд шагает к ТЕКУЩЕЙ позиции цели (самонаведение =
  обновление вектора каждый тик); контакт (дистанция ≤ 1) → полный
  резолв пайплайна; цель умерла → снаряд летит в последнюю точку и
  тает (или мини-взрыв 1-2 тайла — если AoE-хоуминг).
- Уклонение: AGI-цель может «оторваться» (преследование с
  ограничением поворота/времени жизни 3-5с).
- Сейв: снаряды эфемерны — НЕ сохраняются (как pendingCasts сейчас).
- События: `ProjectileSpawnedEvent(from, to, targetId, kind)` +
  `ProjectileMoved` не нужен (рендерер сам анимирует from→to по
  интерполяции; для VFX-фазы достаточно).

- Плюсы: честное самонаведение (кайт, уклонение, погоня снаряда);
  ложится на UpdateTimer без новой подсистемы.
- Минусы: новая сущность в тике (копеечная); снаряд должен уважать
  LOS-препятствия (или игнорировать — лор «Ци обходит камень»,
  решение при реализации).

### 3.3. Вариант B — «Отложенный хит» (дешёвый, без сущности)

Хоуминг = отложенный резолв: `hitTime = distance / speed` тиков; при
хите цель ещё жива → урон с бонусом точности (шанс промаха ×0.2);
цель мертва/убежала → перенос на ближайшую в 2 тайлах или рассеяние.

- Плюсы: ~60-100 строк, без снарядов.
- Минусы: нет видимого полёта (только визуал-морф от VFX-фазы);
  «самонаведение» фиктивно — снаряд не видно, кайт не работает.

**Рекомендация:** A (настоящие снаряды) — VFX-фаза всё равно захочет
летящие болты; B годится как временная заглушка.

## 4. Порядок внедрения (roadmap, если утвердить рекомендации)

| Эпизод | Что | Объём |
|---|---|---|
| R24 | **Мультибой C (реестр входов)** — снятие participant-гейта, NPC-бои молча, UI-сессия игрока, QA COMBAT_SIM: толпа бьёт игрока | 1-2 эпизода |
| R25 | **AoE A** — поля TechniqueData, AoEResolver (int-геометрия), залп по целям, AoeImpactEvent, 3 тестовые техники (конус/полукруг/круг) в генератор, friendly-fire по решению | 1-2 эпизода |

но групповой бой делает площади осмысленными.

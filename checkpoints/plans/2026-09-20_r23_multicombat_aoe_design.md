## 0. Текущая архитектура (факты, от которых отталкиваемся)

| Факт | Значение для дизайна |
|---|---|
| `CombatService` = ОДИН бой на мир (`_isInCombat`, `_instigatorId`, `_currentTargetId`, `_currentStage`) | CMB-2: эмерджентная стычка NPC занимает слот, игрок «не участник» |
| `_readinessPermil` — Dictionary per-entity | Уже готово к мультибою ✅ |

| NPC AI: leash/бегство привязаны к состоянию «в бою» (глобальному) | Меняется вместе с моделью боя |

## 1. МУЛЬТИБОЙ (корень CMB-2)

### Вариант A — «Приоритет игрока» (минимальный дифф)

Единственный слот боя остаётся, но слот принадлежит игроку:

- `StartCombat(player, …)` при занятом слоте (NPC-vs-NPC) → **вытеснение**:
  чужой бой завершается нейтрально (`CombatEndedEvent(Victory:false)` без
  лута/киллфида), NPCs возвращаются к блужданию, стартует бой игрока.
- NPC-vs-NPC бои получают таймаут `MaxCombatDuration` (60-120с игровых):
  стычка не висит вечно.
- Плюсы: ~80-120 строк; контракты/сейв/UI не трогаются; риск регресса низкий.
- Минусы: игрок всё ещё строго 1v1 (второй волк ждёт); стычки NPC
  «обрываются на полуслове» (мир дёрганый); групповые бои невозможны.

### Вариант B — «Per-pair бои» (полный мультибой, правильная архитектура)

Состояние боя → `Dictionary<(attacker, defender), CombatState>`:

- Бой = пара. Игрок может участвовать в нескольких парах (толпа врагов),
  свободно входить в чужую стычку. Смерть → конец только своей пары.
- `ICombatService`: `IsInCombat` → `IsInCombat(entityId)` (+ перегрузки),
  `CombatStartedEvent/EndedEvent` получают `CombatId` (пара);
  `CurrentTargetId` → per-entity (`GetCombatTarget(entityId)`).
- NPC AI: leash/бегство переводятся на per-entity состояние боя.
- UI: HUD врага = «текущая цель игрока» (переключение Tab/последний удар);
  killfeed без изменений.
- Плюсы: честные групповые бои; основа для AoE (толпы!) и самонаводящихся;
  мир живёт без обрывов.
- Минусы: ~400-600 строк (CombatService, адаптеры NPC/звери/игрок, AI,
  QA-симы), контрактные изменения расходятся по потребителям, сейв-блок
  combat меняется. 2-3 эпизода.

### Вариант C — «Реестр входов» (гибрид: лёгкий мультибой) ★ рекомендую стартовать

Убираем ПОНЯТИЕ слота для механики, оставляем его для UI:

- Гейт `IsParticipant` УДАЛЯЕТСЯ: атака разрешена любой паре
  живых сущностей (LOS + readiness + свой каст — уже per-entity).
- «Бой» (`CombatStarted/Ended`, HUD-пара игрока, стадии) остаётся
  ОДНИМ — только как UI-сессия игрока: старт = игрок атаковал/атакован,
  конец = цель игрока умерла/убежала/игрок вышел.
- NPC-vs-NPC дерутся «молча»: урон летает через тот же пайплайн,
  killfeed/смерть/лут работают (события per-target уже есть), но
  CombatStarted/Ended для них не публикуются, стейджи не занимаются.
- leash/бегство NPC: переводятся с «глобального боя» на
  «меня атакует X» (per-entity память последнего атакующего — уже
  есть в RetaliateOrFlee из R20).
- Плюсы: ~150-250 строк; толпа бьёт игрока и игрок бьёт толпу;
  события/UI почти не тронуты (NPC-бесшумность уже привычна по
  эмерджентным стычкам); прямой путь к до-апгрейду B позже.
- Минусы: у NPC-боёв нет «сессии» (нет стадий/таймаута — стычка
  идёт до смерти/бегства по HP-правилам AI); CombatEndedEvent
  семантически = «UI-бой игрока завершён».

### Сравнение

| Критерий | A: приоритет | B: per-pair | C: реестр входов |
|---|---|---|---|
| Игрок против толпы | ❌ 1v1 | ✅ | ✅ |
| Чужие стычки не обрываются | ❌ | ✅ | ✅ (но без сессии) |
| Контракты/сейв | не тронуты | меняются | почти не тронуты |
| Объём | ~0.5 эпизода | 2-3 эпизода | 1-2 эпизода |
| Риск регресса | низкий | средний | низкий-средний |
| Путь к AoE/самонаводящимся | мешает (1v1) | идеален | достаточен |
| Групповые бои NPC (войны фракций) | ❌ | ✅ | ✅ (сырой) |

**Рекомендация:** C сейчас (закрывает боль CMB-2, открывает групповой бой),
B — целевое состояние, к которому мигрируем, когда появится скрытая жизнь
мира (войны фракций, стычки групп). C→B миграция чистая: реестр входов
остаётся, «сессии» добавляются поверх.

## 2. ПЛОЩАДНЫЕ ТЕХНИКИ (конус / полукруг / круг)

### 2.1. Модель данных (общая для всех вариантов)

`TechniqueData` + поля (новые, int/промилле, ЗАПРЕТ 3.9):

```
AoeShape:      None | Circle | Cone | Semicircle | Line   (enum)
AoeRadiusTiles:int          // радиус/полудлина (Circle, Semicircle, Line)
AoeHalfAngle:  int deg      // конус: 30/45/60/90
AoeFalloffPermil:int        // урон на краю: 500‰ = ×0.5 (0 = без спада)
AoeMaxTargets: int          // кап целей (баланс: 3/5/8/∞=0)
```

Форма задаётся ГЕНЕРАТОРОМ техник (Subtype=RangedAoe → форма из рецепта
техники; существующие техники не меняются — `None` по умолчанию).

### 2.2. Вариант резолва A — «Мгновенный залп» ★ рекомендую

При резолве каста AoE-техники:

1. Эпицентр/направление: конус/полукруг — от кастера в сторону
   курсора (`TargetMouseX/Y` уже в событиях!) или текущей цели;
   круг — точка курсора (или цель — для NPC-кастеров).
2. `AoEResolver` (новый engine-agnostic класс в Modules/Combat) собирает
   цели в форме: NPC ∪ звери ∪ игрок (позиции, int-геометрия: Чебышёв
   для круга, скалярное произведение для конуса — без float).
3. На КАЖДУЮ цель — полный существующий пайплайн
   `BuildAndExecuteDamageRequest` (11 слоёв: броня/щит Ци/парирование
   честны для каждой цели; falloff = множитель potency per-target
   промилле).
4. Friendly-fire политика (решение нужно): (а) нейтралы задеваются —
   мир опасен, месть включается (реалистично, рекомендую);
   (б) гейт по faction (групповые техники по «своим» не бьют).
5. События для графики: `AoeImpactEvent(shape, epicenterX/Y, radius,
   angle, targets[])` — рендереру хватит для вспышки/формы (фаза VFX).

- Плюсы: мгновенный взрыв (лор огненного шара); честный пайплайн per-target;
  цифры урона над каждой целью — бесплатно (DamageAppliedEvent).
- Минусы: толпа 20+ целей = 20 резолвов за тик (перф ок до ~50).

### 2.3. Вариант резолва B — «Живая зона» (дополнение, не конкурент)

Площадь = Zone-сущность на карте (N тиков): все входящие в форму получают
урон/эффект каждый тик (ливень, огненная стена, поле подавления).
Пайплайн — существующий DoT (ElementalEffectService) + тик зоны.

- Плюсы: тактические длительные поля; reuses DoT-модуль.
- Минусы: НЕ мгновенный взрыв — другая механика (это фаза 2, отдельный
  эпизод; с вариантом A не конкурирует).

**Рекомендация:** A для взрывных техник (конус/полукруг/мгновенный круг),
B потом для контрольных полей. В первую очередь A.

## 3. САМОНАВОДЯЩИЕСЯ ТЕХНИКИ + система выбора цели

### 3.1. TargetingService (фундамент, нужен обоим вариантам)

`ITargetingService` (новый, engine-agnostic):

```
GetTargetsInShape(origin, shape, angle, params)  → List<TargetRef>
SelectTarget(casterId, filter)                   → TargetRef | null
  фильтры: Nearest | LowestHp | HighestThreat | CursorDirection
```

- Игрок: **Tab** — цикл целей в радиусе (UI-подсветка: рамка/аура на
  выбранной цели — событие `PlayerTargetChangedEvent`);
  прицел ПКМ-курсором для конусов/AoE (уже доставляется).
- NPC: ретаргет по угрозе (уже есть) + «не бить своих в спину»
  (Line-гейт для melee-толпы).

### 3.2. Вариант A — «Снаряд как сущность симуляции» ★ рекомендую

`PendingTechnique` + `IsHoming` + `ProjectileSpeedTilesPerTick`:

- При резолве каста хоуминга НЕ наносим урон: создаём Projectile
  (позиция, скорость, targetId, техника, potency) в реестре
  CombatService (тик в UpdateTimer, рядом с pendingCasts).
- Каждый тик: снаряд шагает к ТЕКУЩЕЙ позиции цели (самонаведение =
  обновление вектора каждый тик); контакт (дистанция ≤ 1) → полный
  резолв пайплайна; цель умерла → снаряд летит в последнюю точку и
  тает (или мини-взрыв 1-2 тайла — если AoE-хоуминг).
- Уклонение: AGI-цель может «оторваться» (преследование с
  ограничением поворота/времени жизни 3-5с).
- Сейв: снаряды эфемерны — НЕ сохраняются (как pendingCasts сейчас).
- События: `ProjectileSpawnedEvent(from, to, targetId, kind)` +
  `ProjectileMoved` не нужен (рендерер сам анимирует from→to по
  интерполяции; для VFX-фазы достаточно).

- Плюсы: честное самонаведение (кайт, уклонение, погоня снаряда);
  ложится на UpdateTimer без новой подсистемы.
- Минусы: новая сущность в тике (копеечная); снаряд должен уважать
  LOS-препятствия (или игнорировать — лор «Ци обходит камень»,
  решение при реализации).

### 3.3. Вариант B — «Отложенный хит» (дешёвый, без сущности)

Хоуминг = отложенный резолв: `hitTime = distance / speed` тиков; при
хите цель ещё жива → урон с бонусом точности (шанс промаха ×0.2);
цель мертва/убежала → перенос на ближайшую в 2 тайлах или рассеяние.

- Плюсы: ~60-100 строк, без снарядов.
- Минусы: нет видимого полёта (только визуал-морф от VFX-фазы);
  «самонаведение» фиктивно — снаряд не видно, кайт не работает.

**Рекомендация:** A (настоящие снаряды) — VFX-фаза всё равно захочет
летящие болты; B годится как временная заглушка.

## 6. R23-эп.3 (2026-09-21): интернет-исследование + ответы на вопросы

**Запрос пользователя:** массовые бои в DF/RimWorld и других играх;
лучшие практики; C→B переход (сложность/смысл); friendly-fire
(нейтралы+месть, сопартийцы+ауры); индикация заряженной техники и кнопка
спуска; неинформативная панель быстрого доступа; хоуминг A подтвердить.

### 6.1. Как массовые бои делают в эталонных играх

| Игра | Модель | Что берём |
|---|---|---|
| **Dwarf Fortress** | Никаких «боёв-сессий»: каждый агент держит свой список целей, бьёт по personal cooldown; все соседние бьют одновременно. Бой — НЕ сущность, чистая эмерджентность | «Бой» как сущность не нужен механике — только UI. Подтверждает вариант C (реестр входов = df-модель поверх готового пайплайна) |
| **RimWorld** | Melee = пер-пара атакующий→цель; «only one pawn per cell can attack the same target» + пешки не стакаются в клетке → **геометрический лимит толпы** (до ~8 соседей). Melee-block: 1-2 фронтовых в проёме, стрелки за спинами — тактика через позиции, НЕ через системные лимиты | Мягкий лимит толпы через занятость клеток (у нас 1 сущность на тайл — лимит уже встроен!). Line-гейт melee «не бить своих в спину» — в TargetingService |
| **RimWorld (FF)** | Friendly fire: safe radius вокруг стрелка (союзники рядом не страдают), storyteller-множитель FF, дикие пули перехватываются. Гранаты/AoE бьют ВСЕХ | Для AoE: нейтралы задеваются (решение пользователя). Для future-ranged: опция safe radius 1-2 тайла от кастера |
| **Mount & Blade** | Толпа на игрока без искусственных лимитов; игрок сам держит 1-2 врага на линии (backpedal/strafe) | «Внимание на одной цели» = позиционирование, не система. Наш AttackThreshold/readiness уже даёт «не все бьют одновременно» — этого достаточно |
| **Souls-like / UE5 attack tokens** | Пул разрешений per-target: AI захватывает токен, остальные кружат и ждут. Спасает fairness в экшн-играх | Для симулятора-колонии НЕ канон (жестокий мир честнее). Но опция для HuntingPack-координации в будущем (стая «разумно» атакует) |

**Общий вывод:** во всех колони-симах состояние боя пер-атакующий /
пер-пара, глобального слота нет. UI-сессия (HUD врага, стадии) —
надстройка. Наш вариант C = Industry Standard для этого жанра;
B (сессии пар) = DF-модель + формальные сессии для будущих войн фракций.

### 6.2. Ответ: старт с C → переход на B (сложность/смысл)

**C → B это надстройка, не переделка.** Что конкретно остаётся/меняется:

| Кусок кода | C (реестр входов) | B (per-pair сессии) поверх C |
|---|---|---|
| Гейт участника `ExecuteAttack:563` | удаляется | НЕ возвращается (остаётся удалён) |
| `_isInCombat/_instigatorId/_targetId/_stage` | UI-сессия игрока (как есть) | + `Dictionary<(a,d), PairState>` для NPC-пар; UI-поля остаются |
| `CombatStarted/EndedEvent` | только UI-пара игрока | + CombatId в контракты; NPC-пары публикуют тихие варианты |
| `pendingCasts` defender-резолв (:671/:759 «instigator?target:instigator») | defender = заявленный targetId для не-участников UI-боя | per-pair: цель запомнена в паре |
| NPC-месть | через `DamageAppliedEvent` → `RetaliateOrFlee` (УЖЕ работает per-target) | то же + OnCombatStarted-ветка для NPC-пар |
| Сейв combat-блок | почти не тронут | + сериализация списка пар |
| QA | COMBAT_SIM: толпа бьёт игрока | + тесты пар NPC-NPC, таймаутов |

**Оценка:** старт B сразу = 2-3 эпизода; C = 1-2 эпизода; миграция
C→B потом = **+1-2 эпизода** (300-500 строк: словарь пар, контракты
+CombatId, сейв-блок, адаптеры NPC). Итог по времени сопоставим
(B сразу ≈ C потом+миграция), но C:

- закрывает боль CMB-2 уже в этом цикле (толпа бьёт игрока);
- разбивает риск на два мелких шага вместо одного крупного;
- даёт ранний плейтест — если почувствуем, что «сессий» для стычек
  NPC и не понадобится (мешает ли, что волк дерётся «без сессии»?),
  сэкономим эпизод целиком.

**Смысл B появляется, когда нужны:** войны фракций (сессия = объект
для хроники/участия), таймауты стычек, «вступить в чужой бой» как
событие. До этого C семантически достаточен. **Двойной работы нет:
каждая строка C остаётся в B.** Рекомендация не меняется: стартуем C.

### 6.3. Friendly-fire: месть нейтралов (решение принято)

Пользователь: «нейтралов задевать — месть включается, мир жесток».

**Механика почти бесплатна:** `NPCAIService.OnDamageApplied` (:515-527)
уже конвертирует любой DamageAppliedEvent в угрозу + `RetaliateOrFlee`.
AoE-вариант A прогоняет каждую цель через полный пайплайн
(BuildAndExecuteDamageRequest) → DamageAppliedEvent на нейтрала →
месть включается сама. Задевать = гневать. Никакого нового кода.

**Осторожность игрока** появляется сама: конус сквозь деревню = толпа
мстящих. Киллфид/лог уже показывает источники урона.

### 6.4. Сопартийцы и «настройка техник под ауры»

**Факт:** сопартийцев-игрока в проекте пока НЕТ (GROUP_SYSTEM — группы
NPC: стаи/патрули; TRANSITION_SYSTEM — спутники в путешествиях).
Фракции не реализованы.

**Сложность самой механики — низкая** (когда будет party): в
AoEResolver перед пайплайном per-target фильтр:

```
if (tech.SpareAlliesPermil > 0                // освоена «бережная» версия
    && targetHasAuraOf(caster))               // party-aura сигнатура
    potencyPermil = falloff(tech.SpareAlliesPermil);
```

— 10-20 строк в резолвере + поле TechniqueData (генератор выдаёт для
техник высоких уровней: «Пламя, пощадящее своих»). Лор = D&D Careful
Spell («бережное заклинание»): мастер жертвует частью силы ради точности.

**Что реально дорого — зависимости:** party/фракции, member-иерархия,
стабильная идентификация «свой» в бою. Это будущая система (R30+).
**Решение:** в R25 резолвер получает ХУК (virtual «SpareCheck»,
всегда false в v1) — когда появятся сопартийцы, механика включается
без переделки AoE. Слагаемые уже сейчас спроектировать.

### 6.5. Индикация заряда + кнопка спуска (проблема подтверждена аудитом UI)

**Подтверждено кодом:** HotbarPanel (654 строки) показывает ТОЛЬКО
кулдаун-занавес + Qi-достаточность. События зарядки
(Started/Progress/Completed/Cancelled) и HeldTechniqueChangedEvent
существуют, но подписан только QA-дебаггер ChargeSimDebug. Спуск =
повторное нажатие той же клавиши (HotkeysWindow:150 подсказывает) —
но UI никак это не показывает.

Данные для UI уже в событиях:
- `TechniqueChargeProgressEvent`: ChargedQi/QiCost (полоса заполнения),
  PotencyPermil 1000→2000 (сегмент overcharge);
- `HeldTechniqueChangedEvent`: TechniqueId/Potency/Element (удержание);
- `AuraHoldService`: ChargedQi тает 1%/тик → рассеивание при QiCost/2
  (таймер жизни удержания).

**Идея 1 — «Слот-центричная» (рекомендую):**
- Заряжается: слот техники — полоса снизу-вверх (изумрудная), рамка
  пульсирует; цифра % по центру.
- Overcharge: полоса янтарная над 100%, подпись «×1.3» (potency).
- Удержание в ауре: слот получает «аура-рамку» (цвет Element) +
  мини-таймер декея; тост «В ауре — Z/повтор для выпуска».
- Кнопка спуска: над хотбаром появляется широкая кнопка «▶ ВЫПУСТИТЬ
  (Z)» — только пока есть удержание; клик = спуск. Плюс подсветка
  слота удержанной техники.
- Плюсы: всё в одном месте, ноль новых панелей. Минусы: периферийное
  зрение (низ экрана).

**Идея 2 — «CastBar по центру» (WoW-стиль):** полоса каста над
хотбаром по центру (имя + ChargedQi/QiCost + overcharge-сегмент);
при удержании полоса не исчезает, а сжимается в постоянный индикатор
с таймером. Плюсы: мгновенная читаемость. Минусы: +1 сущность UI,
занимает центр экрана.

**Идея 3 — «Аура-медальон» (правый-низ):** круглый виджет у угла
хотбара: пусто/заполняющийся круг/пульс-полный/янтарное кольцо
удержания + клик = спуск. Плюсы: лор-точность («техника в ауре»).
Минусы: далеко от слота, глаз бегает.

Кнопка спуска — варианты ввода: (а) как сейчас повтор-Z + подсветка;
(б) отдельная кнопка UI над хотбаром (в идеях 1-3); (в) хоткей R =
«спустить удержанную» (не требует целиться в слот). Совместимы.

### 6.6. Самонаводящиеся A «Снаряды-сущности» — подтверждено (★)

Выбор A подтверждён пользователем. Практики из ресёрча (Reynolds
steering, gamedev.se, kidscancode Godot-recipe) ложатся на наш тик:

- **Seek к текущей позиции** каждый тик (обновление вектора) —
  базовое самонаведение; предсказание позиции цели (цель + её
  velocity×ETA) — вторая ступень, если захотим «умных» снарядов;
- **Ограничение поворота** — анти-паттерн «turn on a dime»: снаряд
  НЕ разворачивается мгновенно. В int-геометрии: |Δvx|+|Δvy| ≤
  TurnBudget (или 8 направлений, поворот ≤90°/тик) → кайт работает,
  AGI-уклонение осмысленно;
- Время жизни 3-5с + LOS-решение (лор: «Ци обходит камень» —
  игнорировать препятствия в v1);
- Событие `ProjectileSpawnedEvent` → рендерер интерполирует полёт
  (VFX-фаза), тик симуляции не грузится.

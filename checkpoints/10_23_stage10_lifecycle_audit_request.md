## Найденные проблемы (кандидаты, НЕ подтверждённые дефекты)

| ID | Предварительная находка | Почему важна | Приоритет |
|----|------------------------|--------------|-----------|
| ST10-01 | Очередь истощённых ресурсов (`ResourceService._depleted` — координаты + день восстановления) не выглядит частью сохранения или сброса мира; сам `ResourceService` — IDisposable, но без ISaveable/IWorldResettable в декларации; `TileService` восстанавливает тайлы по `ResourceRespawnedEvent` | После загрузки/новой игры расписание старого мира может потеряться либо сработать на координатах уже другого мира | P1-кандидат |
| ST10-02 | Очистка старых трупов реализована (`CorpseService.RemoveOldCorpses(maxAgeGameSeconds)`), но явного вызова из игрового тика не найдено; CorpseService не ITickable | Трупы могут оставаться неопределённо долго, растя число объектов | P2-кандидат |
| ST10-03 | Связь NPC с группами при смерти/удалении: `NPCGroupService` имеет ручные RemoveMember/DisbandGroup и восстановление из сохранения, но автоподписки на события смерти не видно | Мёртвый NPC/лидер может остаться участником группы; состояние группы может пережить save/load неконсистентно | P2-кандидат |
| ST10-04 | `WorldService.BulkAdvanceTicks()` сдвигает календарь сразу на несколько минут, минуя per-tick симуляцию; `WorldModule` сравнивает дату с прошлыми маркерами и публикует календарные события | При скачке через несколько суток DayChangedEvent может выйти лишь один раз; подписчики, считающие события (квесты «прожить N дней», старение), недосчитаются | P2-кандидат |

### Уточнения по находкам

**ST10-01 — расписание респауна ресурсов.** Два разных риска, проверять
раздельно:
1. Сохранение/загрузка: если карта регенерируется, а состояние истощения
   не восстанавливается — ресурс может появиться раньше срока.
2. Тёплая новая игра/загрузка другой локации: если старая очередь не
   очищается, позднее событие респауна может изменить тайл новой карты
   по старым координатам.
Окончательный вердикт зависит от порядка фаз сборки (Reset → генерация
тайлов → RestoreState). Проверять первым.

**ST10-02 — жизненный цикл трупов.** Выяснить, вызывает ли
`RemoveOldCorpses` какой-либо компонент вообще. Если вызова нет, а по
игровому контракту трупы должны иметь TTL — дефект очистки. Если они
должны сохраняться до обыска — это не дефект, а несоответствие ожиданий
документации; менять поведение без подтверждения нельзя.

**ST10-03 — группы NPC.** Проверить смерть лидера патруля, гибель
участника стаи, удаление NPC из реестра — и на текущем тике, и после
Save→Load (восстановление существующей, но мёртвой сущности не означает
активное участие в группе).

**ST10-04 — скачки времени.** Не обязательно неверно для всех систем
(респаун ресурсов сверяет абсолютный день), но квесты «прожить N дней»,
старение и другие событийные подписчики могут считать именно события.
Нужен тест на скачок через несколько дней, конец месяца, смену года.

## Решения

- Это запрос на проверку и доказательства, НЕ утверждение, что все
  четыре дефекта подтверждены.
- Сценарий PT-C02 (смерть игрока с активным агро → возрождение → прежние
  NPC/звери не атакуют) включён в регресс Этапа-10 как повторная
  страховка фикса PT-001 (75b8634) — без объявления физплейтест-пункта
  закрытым на основании симулятора.

## Готовое задание кодеру — Этап 10 (канонический текст, verbatim)

[STAGE 10 AUDIT] World lifecycle, spawn/despawn, resources, corpses, time

Проведи этап 10 по текущему коду игры. Не меняй portal/ и web-portal; не редактируй данные портала. Не закрывай находки только по результату чтения кода — добавь воспроизводимые тесты и логи.

### A. ST10-01 — ресурсное истощение и респаун

Проверь:
1. Истощить ресурс, сохранить игру, загрузить её и проверить, что ресурс не восстанавливается раньше заданного срока.
2. Истощить ресурс, затем начать новую игру в другой локации/с другим размером карты; продвинуть время до срока респауна и проверить, что старая очередь не меняет тайл новой карты.
3. Проверить корректность очереди при повторном истощении и при нескольких ресурсах на разных координатах.
4. Проследить полный порядок Reset → генерация карты → RestoreState и определить, должна ли очередь быть ISaveable и IWorldResettable.

Инварианты: старое состояние мира не воздействует на новый; сохранение/загрузка не дублирует и не сбрасывает прогресс ресурсов вопреки контракту.

### B. ST10-02 — очистка трупов

1. Найти все реальные вызовы `CorpseService.RemoveOldCorpses`.
2. Если трупы должны иметь TTL, проверить, что очистка действительно вызывается во время игры и работает по игровому времени.
3. Проверить удаление трупа: запись в сервисе, визуальный маркер и открытое окно обыска не должны оставаться в устаревшем состоянии.
4. Если TTL не предусмотрен контрактом, зафиксировать это как GAP/неподтверждённую гипотезу, не добавлять очистку без согласования.

### C. ST10-03 — смерть/деспавн участников группы

Проверить смерть лидера патруля, смерть участника группы, удаление NPC и зверя, затем Save → Load.

Инварианты: нет ссылок на несуществующих участников; лидер либо заменяется валидным участником, либо группа корректно расформировывается; мёртвый участник не получает активные групповые команды; состав и маршрут после загрузки согласованы с реестрами NPC/зверей.

### D. ST10-04 — скачки времени

1. Выполнить `BulkAdvanceTicks` через несколько игровых дней, конец месяца и смену года.
2. Проверить DayChangedEvent, MonthChangedEvent, YearChangedEvent, квесты на прожитые дни, старение и респаун ресурсов.
3. Сверить календарную дату с результатом каждого подписчика.
4. Отделить намеренно пропущенные per-tick эффекты от календарных эффектов, которые должны учитывать весь пропущенный интервал.

### E. Дополнительный lifecycle-регресс

- New Game → Main Menu → New Game несколько раз в одном процессе.
- New Game → Save → Load → Save → Load.
- Проверить, что нет дублированных NPC/зверей/трупов, устаревших подписок, двойных респаунов и растущих счётчиков сущностей.
- Отдельно повторить сценарий PT-C02: смерть игрока с активным агро → возрождение → прежние NPC/звери не атакуют без новой причины.
- Не считать пункт физического плейтеста пройденным на основании симулятора.

### F. Доказательства и отчёт

1. Добавить `Stage10WorldLifecycleTruthSimDebug.cs` с явными assertions для воспроизводимых сценариев.
2. Подключить запуск через `GODOT_STAGE10_DEBUG=1` в `tools/qa_regression.sh`, не ломая существующие батчи.
3. Запустить сборку и headless Godot-тесты; приложить фактические stdout/stderr и exit codes.
4. Сохранить:
   - `checkpoints/10_23_stage10_lifecycle_report.md`
   - `checkpoints/10_23_stage10_lifecycle.log`
5. Если .gitignore исключает лог, добавить точечное исключение только для требуемого артефакта.
6. В отчёте указать commit SHA, команду запуска, версии Godot/.NET, количество assertions и результаты PASS/FAIL; для каждой находки — шаги воспроизведения, ожидаемое/фактическое поведение и ссылку на лог.
7. Исправления вносить только для подтверждённых дефектов отдельными функциональными коммитами. Для каждого повторить тест, который до исправления воспроизводил проблему.
8. Никаких изменений в portal/ или web-portal.

Не заявляй PASS, если тест не запускался или результат нельзя подтвердить логом.

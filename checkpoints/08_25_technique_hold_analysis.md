## 2. Как работает каст СЕЙЧАС (gap-анализ кода против доков)

### 2.1. Реализация (код, HEAD 418ce7a)

```
Z (или клик в панели T)
  → TechniqueCastRequestedEvent            [GameWorldController:623 / TechniquesPanel:188]
  → PlayerTechniqueCaster.OnCastRequested  [Modules/Player/PlayerTechniqueCaster.cs:86]
      ├── проверки: изучена? Cultivation? цель в радиусе? (Combat)
      └── TechniqueService.UseTechnique    [Modules/Combat/TechniqueService.cs:274]
            ├── кулдаун = 0?
            ├── currentQi >= QiCost?       ── Ци СПИСЫВАЕТСЯ ЦЕЛИКОМ МГНОВЕННО
            ├── QiConsumeRequestEvent(-QiCost)
            ├── кулдаун установлен
            └── мастерство +0.01
  → AttackIntentEvent (для Combat)
  → CombatService                          [Modules/Combat/CombatService.cs:306]
      ├── castTime = tech.CastTime         ── фиксированное поле из генератора
      ├── castSpeedPermil = 1000 + conductivityPermil/100   ── проводимость ПОЧТИ НЕ ВЛИЯЕТ
      │     (cond=2780‰ → ×1.027)
      ├── effectiveCastTime > 0.15с → PendingTechnique (ГЛОБАЛЬНЫЙ на весь бой!)
      └── тикание → применение урона
```

Ключевые отклонения от замысла:
- **Ци тратится мгновенно и целиком** (UseTechnique), а не заполняет технику;
- **проводимость почти не влияет** на скорость (×1.027 при cond 2780‰);
- **PendingTechnique один на весь бой** (известный баг: NPC при смене цели
  может ударить себя — чекпоинт 08_25, «Найденные проблемы» №1);
- **TechniqueChargeService** (`Modules/Combat/TechniqueChargeService.cs`) —
  сервис накачки с правильной моделью (зарядка тиками, расход Ци тиками,
  potency 1000→2000‰, отмена с возвратом 50%) — **перенесён из legacy,
  зарегистрирован в DI, но СПИТ**: никто не вызывает StartCharge в пайплайне
  игрока; CombatService берёт у него только potency (всегда дефолтные 1000‰).

### 2.2. Что говорят доки («готовые правила»)

`docs_v2/02_systems/TECHNIQUE_SYSTEM.md`:

- **§5.1** — пайплайн: проверка → расчёт → тратаЦи → кулдаун → мастерство;
- **§5.2** — qiCost = floor(baseCapacity × 2^(L−1));
- **§5.3** — **время каста = qiCost / effectiveSpeed**, где
  effectiveSpeed = conductivity × (1 + cultivationBonus) × (1 + masteryBonus);
- **§4** — capacity = qiCost-масштаб × (1 + mastery×0.005) — структурная
  ёмкость (потолок перезарядки);
- **§7** — дестабилизация: вливаемое Ци > ёмкости → излишки рассеиваются,
  урон практике 50% от излишка.

**Вывод gap-анализа:** модель заполнения из запроса пользователя — это
**ровно §5.3 доков** (написаны «моделью 5.2», не реализованы). Код вместо
этого делает мгновенный расход + фиксированный CastTime. То есть задача
№1 запроса — **догнать реализацию до уже принятых правил**, а не придумать
новые. Идея №2 (задержка/аура) — новое правило, которого в доках ещё нет.

### 2.3. Числовая проблема «готовых правил» (важно!)

Проводимость практика = coreCapacity / 360 с (медитационный масштаб,
QI_SYSTEM §5):

| Уровень | Проводимость | qiCost Combat-melee | Время заполнения по §5.3 |
|---------|--------------|---------------------|--------------------------|
| L1 | 2.8 Ци/с | 64 | **23 с** |
| L3 | 18.7 Ци/с | 256 | 13.7 с |
| L5 | 125.7 Ци/с | 1 024 | 8.1 с |
| L9 | 5 690 Ци/с | 16 384 | 2.9 с |

Литеральное применение §5.3 даёт 23-секундный «каст» базовой техники L1 —
это медитационный темп, не боевой. Проводимость считалась для поглощения
Ци из среды за полный цикл (360 с), а не для форсированного пропускания
Ци через боевые меридианы.

**Предложение:** формула доков сохраняется, но с боевым множителем канала:

```
chargeRate = finalConductivity × K × (1 + mastery × 0.005)   [Ци/тик]
fillTicks  = qiCost / chargeRate
```

K = GameConstants.CombatChannelMult (лор: «боевой прогон» меридиан против
осторожного медитативного поглощения). Балансовая таблица:

| K | L1 (64) | L3 (256) | L5 (1024) | L9 (16384) |
|---|---------|----------|-----------|------------|
| ×8 | 2.9 тика | 1.7 | 1.0 | 0.36 |
| ×12 | 1.9 | 1.1 | 0.68 | 0.24 |
| ×20 | 1.1 | 0.68 | 0.41 | 0.14 |

Кривая правильная: с ростом уровня практики относительно дешевеют техники
(ёмкость ядра растёт быстрее qiCost) — «ветераны кастуют быстро».
**Рекомендация: K=12 стартово** (L1 базовая техника ~2 тика, тяжёлые
AoE/beam подтипы с baseCapacity 32 и qiCost 32 — быстрее;Ultimate ×2 Ци —
дольше), финальная калибровка — плейтестом. Реакционные техники
(Dodge/Block) с малым qiCost заполняются <0.3 тика — фактически мгновенно,
UX не ломается.

Альтернатива (если K не нравится): нормированная модель —
castTime_эфф = CastTime(таблица подтипов) × condExpected(L) / finalConductivity.
Плюс: темп не зависит от уровня. Минус: проводимость перестаёт быть
«настоящей» величиной расхода Ци, расходим с духом §5.3. В таблицу решений.

## 3. Предлагаемая унифицированная модель

```
┌─────────┐   ┌──────────────────┐   ┌──────────────┐   ┌───────────────┐
│ НАЖАТИЕ │──▶│  ЗАРЯДКА         │──▶│  ГОТОВА      │──▶│ СРАБАТЫВАНИЕ  │
│ Z/клик  │   │  Ци течёт тиками │   │  (qiCost     │   │ (эффект по    │
└─────────┘   │  ≤ chargeRate    │   │   достигнут) │   │  типу)        │
              └──────────────────┘   └──────────────┘   └───────────────┘
                 │ отмена/стан:            │
                 │ возврат 50%             ├── аура СВОБОДНА → подвязка в ауру
                 ▼                         │   (вариант В; см. §4)
              рассеяние                    └── аура ЗАНЯТА → немедленный выпуск
                                             (второе нажатие = выпуск удерживаемой)
```

Расширение поверх §5.3 (опционально, стадия 2): продолжение накачки сверх
qiCost в пределах capacity (§4) → **перезарядка**: potency 1000→2000‰
(формула уже есть в TechniqueChargeService:122 — она была написана ровно
под это окно). Сверх capacity → дестабилизация §7 (урон себе, рассеяние
излишков). Это делает спящую систему накачки и правило дестабилизации
досягаемым геймплеем без новых сущностей.

## 4. Варианты привязки «задержки» — сложность и привлекательность

### Вариант А: флаг на конкретных техниках

Модель: TechniqueData/LearnedTechnique + поле `CanHold` (или
`HoldBehavior`); генератор/таблицы решают, какие подтипы/грейды умеют
«зависать».

- **Сложность: НИЗКАЯ-СРЕДНЯЯ.** Поле + таблица подтипов + маркер в UI
  (⏳). ~50–80 LOC поверх общей модели.
- **Игровая привлекательность: 6/10.** Дает точечный баланс (тяжёлые
  нюки держатся, спам-техники нет), но правило непрозрачно: «почему эта
  держится, а та нет?» — игроку нужно учить таблицу; тактика фрагментарна.
- **Риск:** балансная мигрень на каждую новую технику в генераторе.

### Вариант Б: привязка к слоту

Модель: поведение «задержки» определяет слот (слот изучения §12 или
слот хотбара пояса).

- **Сложность: СРЕДНЯЯ.** Слоты §12 — это **память** (сколько техник
  знает практик), хотбар пояса — **физические быстрые слоты расходников**.
  Вешать поведение на хранилище — семантический конфликт, потребует
  новой сущности «поведение слота» + UI-различения слотов.
- **Игровая привлекательность: 3–4/10.** Ригидно, неинтуитивно, ломает
  ментальную модель «слот = вместимость». Плюс конфликт с поясом
  (слоты пояса уже заняты расходниками).
- **Рекомендация: отклонить.**

### Вариант В: все техники, аура держит ОДНУ ⭐ рекомендация

Модель: единое правило для всех техник — зарядка завершена →
если аура свободна, техника **подвязывается в ауру** (ожидает выпуска);
если занята → **срабатывает немедленно**. Повторное нажатие клавиши
выпускает удерживаемую.

- **Сложность: СРЕДНЯЯ.** Новая сущность HeldTechnique (единственный
  слот) + события + визуал ауры + сохранение. ~350–500 LOC поверх стадии
  зарядки. См. §8, стадия 1.
- **Игровая привлекательность: 9/10.** Единое правило, которое игрок
  понимает за один бой; лёгкие техники (Dodge/Block/MeleeStrike) при K=12
  заполняются почти мгновенно → «двухфазность» не мешает в мелких драках,
  а тяжёлые техники создают решение «держать или стрелять».
- **Ключевые игровые эффекты:**
  - **подготовка к бою** (зарядил до контакта — но аура ВИДИМА, см. риски);
  - **комбо**: формация Amplification → выпуск; dash → выпуск с новой
    позиции; щит держится, пока заряжается атака;
  - **контригрок** (будущее): видишь ауру врага = знаешь, что он держит;
  - **жанровый троп** культивации («держать технику в ауре») —
    тематическое попадание.
- **Естественный балансный ограничитель:** один слот ауры = нет
  «батареи» из заряженных техник.

### Итоговая матрица

| Критерий | А (флаг) | Б (слот) | В (аура=1) |
|----------|----------|----------|------------|
| Сложность реализации | низкая-средняя | средняя | средняя |
| Прозрачность правила | 5/10 | 3/10 | **9/10** |
| Тактическая глубина | 6/10 | 4/10 | **9/10** |
| Балансная управляемость | высокая (точечно) | низкая | средняя (декей/стан) |
| Совместимость с доками | нейтрально | конфликт §12 | **дополняет §5.3** |

**Рекомендация: вариант В**, с оговоркой — оставить в модели данных
`HoldPolicy { Normal, CannotHold, OnlyHold }` (по умолчанию Normal) как
**балансовый предохранитель** будущего (например, Ultimate-техники можно
позже пометить CannotHold). Это элементы А внутри В без его недостатков.

## 5. Взаимодействие с существующими правилами

| Правило/система | Решение в новой модели |
|-----------------|------------------------|
| **Кулдаун** | стартует в момент **выпуска** (не начала зарядки — иначе удержание = потерянный кулдаун). Отмена зарядки → кулдауна нет |
| **Мастерство §10** | растёт при **выпуске** (как сейчас, в UseTechnique-завершении) |
| **Дестабилизация §7** | становится досягаемой: перезарядка сверх capacity → урон себе 50% излишка, рассеяние. Ровно по доке |
| **Потency (спящий код)** | TechniqueChargeService.PotencyPermil 1000–2000‰ — окно [qiCost..capacity]. GetTechniqueDamage уже применяет пермил |
| **Формации** | Amplification-зона повышает урон выпуска (уже работает); Gathering ×2 ускоряет медитативное поглощение (не зарядку — иначе цикл) |
| **Время** | зарядка в ТИКАХ: на Fast реальная длительность сжимается, количество на игро-сутки постоянно (решение сессии 08_25 о «времени как ресурсе») |
| **Медитация** | взаимоисключающа с зарядкой (медитация = аккуратное поглощение); вход в медитацию → отмена зарядки с возвратом 50% |
| **Движение при зарядке** | разрешено; опция «замедление ×0.5» — вопрос к пользователю (см. §10) |
| **Урон по зарядке** | НЕ прерывает (иначе неиграбельно); прерывают стан/оглушение/смерть |
| **Qi-буфер/щит** | независимая система, сосуществует |
| **Cultivation** | пассивна — не затронута |
| **NPC** | сейчас атакуют псевдо-техникой "npc_strike" (NPCModule:132) без данных техники → зарядочная модель сначала только для игрока; паритет NPC — стадия 2. Отметить в доках как осознанную временную асимметрию |
| **Save/Load** | активные зарядки + удерживаемая техника сериализуются (ISaveable) |

Попутно **закрывается известный баг** «глобальный PendingTechnique»
(чекпоинт 08_25, проблема №1): per-attacker зарядки в
TechniqueChargeService заменяют единственный _pendingTechnique —
NPC больше не сможет «ударить себя» при смене цели.

## 7. Игровая привлекательность — итоговая оценка

**Базовая модель заполнения (§5.3):**
- (+) проводимость становится **реальным боевым статом** (сейчас ×1.027 —
  мусорное значение); перки на проводимость и зарядники (CHARGER_SYSTEM)
  получают боевой смысл;
- (+) вес техник: тяжёлая AoE реально «читается долго» — тактическое окно
  для противника;
- (+) экономика Ци: можно НАЧАТЬ технику, которую не хватит Ци закончить
  (прервётся на текущей мощности) — осмысленные решения о ресурсах;
- (+) досягаемыми становятся дестабилизация и перезарядка (potency) —
  уже описанные, но мёртвые правила;
- (+) соответствие докам: реализация догоняет принятые правила;
- (−) темп боя замедляется (снимается множителем K + мгновенные лёгкие
  техники);
- (−) нужен UI прогресса и правила прерываний (в плане).

**Задержка в ауре (вариант В):**
- (+) новое тактическое измерение: подготовка, тайминг, комбо с рывком
  и формациями;
- (+) контр-игра: аура видима;
- (+) trop-попадание в жанр культивации;
- (+) единое правило, нулевая таблица исключений на старте;
- (−) альфа-страйк из засады (снимается: декей 1%/тик удержания, видимость
  ауры, прерывание станом);
- (−) сложность ввода-вывода (индикаторы) и сейвов — учтено в стадиях.

**Вердикт:** привлекательность высокая, обе части взаимно усиливаются
(заполнение без удержания — половина механики; удержание без заполнения —
невозможно). Рекомендуется к реализации в две стадии.

## 8. Стадийный план (для подтверждения)

> ⏸ Никакой код не пишется до явного подтверждения пользователем.
> Каждая стадия = отдельный чекпоинт + коммит + верификация.

- **Стадия 0 — «Модель заполнения»:** зарядка тиками по проводимости
  (K=12), расход Ци тиками, отмена 50%, события, UI-прогресс, сейвы,
  GODOT_CHARGE_SIM, удаление глобального PendingTechnique.
  *Критерий готовности:* тайминги по таблице §2.3, COMBAT_SIM PASS,
  лёгкая техника Z-Z-Z не медленнее текущей.
- **Стадия 1 — «Аура-слот» (вариант В):** удержание одной техники,
  второй нажатие = выпуск, декей 1%/тик, прерывание станом, визуал ауры,
  HUD, сейвы. *Критерий:* hold→release сценарий в симе; скриншот ауры.
- **Стадия 2 — опционально (отдельный план):** перезарядка при удержании
  (potency 1000–2000‰ + дестабилизация), паритет NPC, HoldPolicy.

## 9. Документация «5.2 → 5.3» — оценка

**Фактическое состояние:**
- `docs/` (v1) — историчны: пути Unity, дисклеймеры «НЕТ КОДА», файловая
  структура Scripts/Techniques/*. 50+ файлов, массовое переписывание
  нецелесообразно.
- `docs_v2/` — актуальный design spec (engine-agnostic). Найденные
  расхождения при этом анализе:
  1. TECHNIQUE_SYSTEM **§5.1 против §5.3** — внутреннее противоречие
     (тратаЦи до каста против времени заполнения); унифицировать под
     модель заполнения;
  2. §5.3 пример даёт 15 с каста — нужен K-множитель и балансовая
     таблица (§2.3 этого анализа);
  3. TECHNIQUE_USAGE_REPORT.md — устарел (до Qi-этапов);
  4. COMBAT_SYSTEM — секция pending-каста устареет после стадии 0;
  5. QI_SYSTEM — нужна подсекция «боевой прогон меридиан» (K).

**Стратегия (рекомендация):**
1. **Не переписывать всё скопом.** Правила 5.2 содержат выверенные
   балансовые числа и лор; генеративное переписывание рисками их потерять.
2. **Эволюция вместе с кодом:** каждая стадия реализации обновляет
   ЗАТРОНУТЫЕ доки (+статус «сверено с кодом», дата, версия модели) —
   это уже часть правила процесса с чекпоинтами.
3. **Архивный баннер** в docs/README («историческая версия, источник
   истины — docs_v2/»).
4. После стадий 0–1: патч TECHNIQUE_SYSTEM (§5 унификация + новая
   секция «Аура-задержка»), QI_SYSTEM (боевой K), COMBAT_SYSTEM
   (per-attacker зарядка), STATUS-заголовки.

Оценка объёма: ~4 докcа × 30–60 мин — **после** подтверждения плана,
вместе с соответствующей стадией кода.

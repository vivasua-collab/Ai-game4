## 2. Развилки и решения

### 2.1. P1-9 — fail-closed c полной диагностикой, БЕЗ rollback (P2-20)

**Решение:** зеркально startup-контракту P2-13 (который аудитор отдельно
похвалил в Фазе 4-вердикте):

- одна попытка = ВСЕ домены получают `ResetWorld()` (сбросы доменов
  независимы — продолжение цикла после провала не создаёт новых зависимостей,
  зато даёт полную картину провалов в одном AggregateException);
- исключения агрегируются → `AggregateException` наружу из
  `ExecuteAsync()` с именем каждого домена;
- SceneOrchestrator: `MarkAsFailed` + `SceneAssemblyFailedEvent` + rethrow →
  `GameSession.NewGame/LoadGame` → сессия в `MainMenu`. Частично-сброшенный
  мир НЕ собирается дальше (фаза 0 — «последующие фазы считают мир чистым»).

**Rollback отклонён** (P2-20 аудитора): reset не транзакционен; контракт =
«сброс упал → world-transition неуспешна», а не «мир частично жив».
Fake-rollback маскировал бы грязь. Единая семантика с LoadGame-путём
(GameSession.ResetWorld-цикл — исключение выходило наружу и там; теперь
обе двери одинаковы — то самое «две разные семантики одного контракта»
из Фазы 6 устранено).

Страж: сим I (I1 исключение покидает фазу; I2 агрегат называет домен;
I3 все домены диагностированы за попытку; I4 MarkAsCompleted недостижим).

### 2.2. P1-10 — два слоя: транзакция в GameEntryPoint + идемпотентные Start()

Аудитор предложил два варианта: A (все IStartable строго идемпотентны) /
B (rollback/Stop успешных при провале). Реализованы **оба слоя защиты**
(B-контракт Stop() не вводился — см. ниже):

**Слой 1 — GameEntryPoint (главный):** стартовая попытка = транзакция с
точкой продолжения. `_startedModules` (HashSet по ссылке, живёт через
ретраи): успешно завершившие `Start()` модули при ретрае **пропускаются**;
ретраятся только провалившийся и ещё не стартованные. Откат (Stop/Dispose)
успешных НЕ делается: их инициализация валидна, тики до успешного бута
заглушены (P2-13) — они ничего не «пропустили». G3-контракт сохранён:
ретрай не игнорируется, провал повторяется с полной диагностикой.

**Слой 2 — идемпотентные Start() всех lifecycle-модулей** (директива
аудитора «пройти по всем IStartable, а не латать только NPC»): гвард
`_startCompleted` в каждом из 22 Start() (17 IModule + SeveredDebuffSystem,
AnimalService, TechniqueSlotService, PlayerCombatAdapter,
PlayerTechniqueCaster; TradeModule — поверх существующего
dispose-старого-паттерна). Флаг ставится **только при успешном
завершении** — провал остаётся ретраимым (нет маскировки полу-старта).
Слой закрывает и прямые вызовы вне бута: например,
`GameWorldController._Ready()` вызывает `CombatAdapter?.Start()` /
`TechniqueCaster?.Start()` при каждой инстанциации сцены мира — гвард
гасит потенциальную двойную подписку на повторной сборке.

**Почему не B (Stop-контракт):** у IStartable нет Stop()/rollback в
архитектуре; вводить его ради редкого boot-retry — расширение поверхности
API с риском рассинхрона контрактов Dispose/ResetWorld/Stop. Двойной слой
(транзакция + идемпотентность) закрывает P1-сценарий аудитора полностью
при существующих контрактах. Бэклог P2-10/P2-11 сужен: осталась
идемпотентность `Initialize()` сервисов при ЧАСТИЧНОМ провале модуля
(Start() упал между двумя Initialize — повторный Start перезапустит
успешную часть; в boot-пути закрыто слоем 1, прямой вызов — вне контракта).

Страж: сим J (J1 первый бут провален агрегатом, успешный модуль подписался
1 раз; J2 SubscriberCount стабилен за ретрай; J3 StartCalls 1/1; J4
проваленный ретраится).

### 2.3. P1-12 — фильтрация Pure ДО расчёта буфера

**Решение — рекомендация аудитора дословно:** «pure-damage должен быть
отфильтрован до вызова CalculateBufferAbsorption(), а не после».
`isPureDamage` вычисляется до ветки буфера; `if (bufferActive &&
!isPureDamage)` — Pure не входит в `CalculateBufferAbsorption()` вовсе:
ни `QiConsumeRequestEvent` (игрок), ни `TryConsumeQi` (NPC), поглощение 0,
пробитие = postDefenseActionDamage. Удалён пост-фактум-блок
(«обнуление после списания») — источник дефекта.

**Броня к Pure применяется как раньше** — осознанно: аудитор сам отметил
(Фаза 9), что Pure не был объявлен режимом, обходящим ВЕСЬ defense-пайплайн,
и без подтверждения спецификации он броню не трогал. Контракт закреплён в
COMBAT_SYSTEM §5: Pure = абсолютный урон для Ци-буфера; броня/материал —
обычный путь. Комментарий кода («игнорирует броню и Ци-буфер») исправлен
на фактический контракт.

Страж: сим K (K1/K2 игрок: absorbed=0, Ци 1000→1000; K3 NPC: Ци 500→500,
TryConsumeQi не вызван; K4 контроль Physical: absorbed=80, Ци 500→100 —
буфер жив, фикс не отключил обычный путь).

## 4. P2-22 — runtime-диагностика по запросу Фазы 7 (без фикса)

Аудитор просил «конкретный runtime-чек на P1-9 и EventBus edge case» и в
Фазе 7 — «три runtime-проверки: P1-9, P1-10 и P2-22». P2-22 поставлен как
**диагностическая секция L** сима №19 (вердикт не гейтит — фикс в
«следующем слое» по директиве Фазы 10):

```
diag: L queued-drain maxDepth=3, deliveries=6 (цепочка 6) —
guard ПОТЕРЯН в дрене: queued self-publish идёт прямой рекурсией
```

Сценарий (ограниченная self-publish цепочка, StackOverflow исключён):
внешний Publish(1) → queued(2) → дрен: InvokeHandlers(2) БЕЗ T в
`_publishing` → Publish(3) идёт напрямую (рекурсия), Publish(4) снова
queued (внутри прямого), Publish(5) напрямую… Глубина рекурсии растёт
(наблюдаемая 3 при контракте ≤2; паттерн чередуется queue/direct —
каждый второй уровень уходит в рекурсию). Вывод аудитора подтверждён
runtime: queued-дрен теряет re-entrancy guard; классификация P2
(нужен патологический self-publish-цикл) — оставлена как бэклог
следующего слоя.

## 2. Ответы на вопросы аудитора (развилки фазы)

### P2-13 — «startup failure = abort или degraded mode?»

**Ответ: abort (FAIL-CLOSED) для startup; tick остаётся fail-open.**

Решение зафиксировано как явный контракт (раньше контракт не был определён —
в этом и был дефект):

- **Все** модули получают `Start()` за одну попытку (полная диагностика:
  если упало три модуля — AggregateException назовёт все три, а не первый).
- Любой провал → `AggregateException` наружу; `_initialized` НЕ
  выставляется; тик-луп заглушён (полуинициализированные модули не
  симулируют и не автосейвят — автосейв в SaveModule завязан на тики).
- `GameBoot` ловит агрегат, `GD.PushError` по каждому провалу, глушит
  `_PhysicsProcess` и не входит в игру/автоматизацию. В headless-QA такой
  бут не печатает VERDICT → сим падает по таймауту как FAIL (раньше
  «тихо зелёный» прогон с проглоченным стартом — это была дыра самого QA).
- Ретрай `Start()` не игнорируется («already initialised»-маска не
  срабатывает на провале), списки startables/tickables пересобираются с
  нуля. Замечание: ретрай повторно стартует и УСПЕШНО стартовавшие модули —
  их идемпотентность это известный P2-10/P2-11-бэклог, в продакшене
  `Start()` вызывается один раз (только GameBoot._Ready).
- Почему НЕ degraded: молчаливое «играем дальше без модуля» — это то самое
  «частично инициализированное состояние становится постоянным», которое
  аудитор пометил как главную опасность; для игры в разработке громкий
  провал строго информативнее. Изоляция сбоя остаётся контрактом
  рантайма (Tick), где она уместна: единичная ошибка в установившемся
  мире не должна останавливать симуляцию.

### P2-12 — «либо использовать _orderedRegistrations, либо официально убрать обещание order»

**Ответ: используем _orderedRegistrations — обещание registration order сохранено и теперь исполняется.**

- `Container` хранит ordered-список (прежде ctor-параметр игнорировался) и
  `ResolveAll` итерирует его.
- Критичная связка: ordered-список согласован со словарём ключей —
  сместившаяся регистрация, не владеющая больше НИ ОДНИМ ключом (хвосты
  prune-а P1-6; self-bound ключ `Register<SaveFileHandler>`, украденный
  форвардом `Register<ISaveFileHandler, SaveFileHandler>`), из ordered
  удаляется. Без этого ResolveAll по ordered **воскресил бы мёртвый
  Modules-дефолт** — P1-6 вернулся бы через другую дверь. Живая
  мульти-интерфейсная регистрация (владеет primary-ключом, форвард-ключ
  мог быть украден соседом — NPC-паттерн, страж C5) остаётся в списке.
- Матчинг по фактическому типу + дедуп по ссылке — без изменений
  (семантика R11 P0-Save). Меняется только порядок: был
  «фактический-но-негарантированный» (Dictionary.Values, ломается
  удалениями), стал «порядок вызовов Register».
- Отдельный Order/priority-механизм НЕ вводим: текущие потребители
  (IStartable/ITickable — GameEntryPoint; ISaveable — агрегатор; фазы
  сцены — отдельный PhaseOrder) обходятся порядком регистрации модулей
  (§1.2 canonical order), это достаточнее и проще.

### P1-6 — «комментарий GameBoot не соответствует семантике контейнера»

**Ответ: закрыто в r32 (до доставки текста Фазы 4) — находка подтверждена,
текст Фазы 4 совпал с нашей реконструкцией.**

Реконструкция по строке итога (контент Фазы 4 в файле отсутствовал) была
верна: `RegisterInstance<ISaveFileHandler>(adapter)` заменял только ключ
`ISaveFileHandler`, concrete-ключ `Modules.SaveFileHandler` оставался жив →
`ResolveAll<ISaveFileHandler>` видел обе реализации, `Resolve<Modules.SaveFileHandler>`
резолвил мёртвый fallback. Фикс r32 — prune хвостов ТОЛЬКО при
инстанс-оверрайде (RegisterInstance): старая регистрация, потерявшая по
этому ключу свой первичный сервисный тип, теряет и forwarding-ключи. NOW
комментарий GameBoot «in place of the Modules-layer default» — правда.
Важное (см. 09_22_r32 §6): наивный prune «смерть primary-ключа ⇒ удалить
форварды» был отвергнут ДВУМЯ живыми регрессиями (Combat→TechniqueService,
Corpse→NPCService) — forwarding-ключи это lifeline мульти-интерфейсного
паттерна. Стражи C1–C5 закреплены, R33 добавил F2 (ResolveAll-гарантия —
ровно один handler после override).

### P2-14 — «архитектурно правильнее construction stack с путём»

**Ответ: реализовано ровно так.**

- `Container` держит `_constructionPath` (стек типов в ТЕКУЩЕЙ цепочке
  конструирования; доступ только под `_lock`, вложенные Resolve рекурсивны
  на одном потоке — Monitor реентерабелен, ThreadStatic не нужен).
- Повторный вход типа в цепочку → немедленный throw с точным путём:
  `Circular dependency detected while resolving '…': CycA → CycB → CycA`
  (формат пути «A → B → C → A» — как в рекомендации аудитора). Без 51-го
  лишнего конструирования.
- Depth>50 остаётся страховкой (циклы через фабрики/Activator путь в
  стеке не оставляют).
- Кэш синглтонов не даёт ложных срабатываний: инстанс кэшируется ПОСЛЕ
  завершения Construct — повторный запрос недостроенного типа это по
  определению цикл (и прежде падал по depth — теперь падает раньше и
  с диагностикой).

## 4. Фиксы R33 (коммит r33)

1. **Container.cs (P2-12):** `Container` хранит `_orderedRegistrations`;
   `ResolveAll` итерирует ordered (комментарий контракта); builder:
   `SetRegistration` согласует ordered со словарём (мёртвая регистрация —
   не владеющая ни одним ключом — удаляется; `OwnsAnyKey`).
2. **Container.cs (P2-14):** `_constructionPath` + проверка повторного
   входа перед Construct + `finally`-pop; `FormatConstructionPath` («A → B
   → C → A»); depth>50 остаётся страховкой; док-буллеты класса обновлены.
3. **GameEntryPoint.cs (P2-13):** fail-closed startup (сбор failures →
   AggregateException; ВСЕ модули стартуют до броска); `_initialized`
   выставляется только при полном успехе; каталог локаций — в общий
   агрегат (R17 WT-3 — стартовый критический шаг); повторный Start()
   пересобирает списки; класс/Tick-доки описывают контракт
   startup=fail-closed / tick=fail-open.
4. **GameBoot.cs (P2-13):** try/catch вокруг `_entry.Start()` —
   PushError по каждому провалу, `_bootFailed` глушит тик-луп, ранний
   return (ни скриншот-автоматизации, ни входа в игру).
5. **Audit0922SimDebug.cs:** секции F (P2-12: порядок B,C,A; ровно один
   handler после override; мульти-форвард дедуп+стабильный порядок),
   G (P2-13: AggregateException с именем модуля; тики не доставляются
   после провала; ретрай не игнорируется), H (P2-14: CycA→CycB→CycA с
   путём; SelfCyc; линейная цепочка без ложного срабатывания) +
   позитивный контроль живого fail-closed бута.
6. **Доки:** DI_AND_EVENTBUS §1.8 «Контракты жизненного цикла и
   ResolveAll»; TESTING_RULES — строка AUDIT0922 (секции F/G/H).

## 3. Ключевые решения и факты

### ST15-001 — двойной путь экипировки NPC (открытие префикса)
Живой путь был ДВОЙНЫМ: `NPCAssemblyService.EquipHumanoid` (легаси, 7 слотов) → затем `NPCSpawnerService.EquipFromGenerator` перезаписывал WeaponMain/60% брони «Матрёшкой». Итог NPC в префиксе: WeaponMain/Head = «Матрёшка», но **WeaponOff/Legs/Feet (+40% Torso) — легаси** (`NameEn='Armor Level N'`, Slot=Torso в чужих слотах). Миграция `EquipHumanoid` на `IEquipmentGenerator` закрыла все слоты: броня по классам слотов (`armor_head/torso/legs/feet`), офхенд — только 1H (TwoHand → детерминированный парный dagger), зарядник Belt — остаётся легаси (канон EQUIPMENT_SYSTEM: «ItemGeneratorService остаётся для consumables/chargers»). **%1000-находка старого аудита (G-1) НЕ реанимирована** — R35 counter-based NextId уже в коде, подтверждено чтением.
Спавнерский `EquipFromGenerator` сохранён без изменений (его логика уровня оружия Enemy+1); известная особенность «NPC регистрирует 2 оружия (EquipHumanoid + спаунерская перезапись)» существовала до этапа и не является потерей данных — отмечена как остаток владельцу.

### ST15-002/007 — семантика валидатора
- **Оружие/броня с нераспознанным классом → Critical-отказ** (раньше IsValid=true при непроверенных границах — «тихий обход валидации»).
- **Аксессуары → документированный skip** (таблиц границ нет; сообщение явно отличает аксессуар от нераспознанного оружия).
- **NaN отвергается** (`float.IsNaN` в CheckFloat; NaN-сравнения оба false — потому прежняя проверка пропускала). ±Infinity и прежде отвергались сравнениями — DISPROVED-часть, проверка оставлена.
- **Enum-гарды до таблиц**: Grade=99 → диагностика Critical, не IndexOutOfRange.
- Живых вызовов Validate(Equipment) на легаси-предметах нет (CheatPanel/GeneratorModule-демо валидируют только «Матрёшку») — Critical-отказ ничего не ломает.
- **G4**: явный неизвестный subtype → ArgumentException (fail-fast); `subtype=null` → случайный класс (документированная норма NPC-пути).

### ST15-004 — fingerprints
Состав расширен до всех механических полей (см. шапку DeduplicationService); формат — инвариантная культура + R (round-trip): культура-зависимость (`ru-RU` давала «2,00» vs «2.00») и F2-схлопывание (3.001≡3.004) устранены. Имена/описания по-прежнему НЕ входят — дубли механически одинаковых объектов должны удаляться (PRE_GENERATION §дедуп).

### ST15-005 — ID и регистрация
- `GenerateTechniqueId`: `tech_{type}_{element}_{grade}_L{level}_{seed:x8}` (было 16-бит `…_{hash:X4}`); формации аналогично. Паттерн = ужефиксированный `ItemGeneratorService.NextId`.
- **Safe-register** в TechniqueRegistry/FormationRegistry: замена только при идентичном fingerprint (идемпотентность «тот же seed → тот же объект» сохранена, E3 PASS до/после); коллизия Id с другим контентом → диагностика + отказ (тихая подмена невозможна). FormationRegistry использует локальную Signature (Formation→Generator-импорт создал бы цикл модулей; состав полей синхронизирован с Fingerprint).
- **Обратная совместимость:** сейв игрока хранит ПОЛНЫЕ снапшоты техник (TechniqueSnapshotDto) — смена формата ID безопасна; NPC-референсы техник при LoadGame и так висячие (PreGen SkipOnLoad, реестры не сохраняются — известный G-13/G-2 остаток вне этапа).

### ST15-008 — жизненный цикл
- `FormationRegistry : IWorldResettable` (+Remove/Clear) — `WorldDomainResetCoordinator.ResetAll` (ResolveAll по фактическому типу инстанса) сбрасывает его на world-transition (постфикс: «сброшено доменов: 37», маркер очищен).
- In-session `NewGame` из Playing отклоняется by design (menu-only) — контракт пересборки проверен операцией координатора (прецедент Stage10-A4/A5).
- `ItemDatabaseService` R17/R35-механика **подтверждена адресно** (H1 fresh-instance restore + счётчики + уникальность; H2 двойной ResetWorld; H4 контракты seed=0; cold-пара НОВЫХ процессов: маркер в каталоге после загрузки, новые ID уникальны) — НЕ переделана, по требованию аудита.
- **Контракт seed=0 задокументирован как ДВА режима** (H4): ItemGeneratorService — seed=0 = авто-счётчик (уникальные ID); Technique/Formation — seed=0 = валидный детерминированный сид (SeededRandom(0)). Оба протестированы.

### Харнес-рефайнинг (задокументировано честно)
1. **A1 → характеристика легаси-генератора**: в префиксе A1 фиксировал легаси-формат (FAIL-доказательство к A3); после миграции сам легаси-формат — не дефект (генератор сохранён для зарядников/расходников + Audit0922-харнес). Критерий A1 уточнён в том же коммите, что и миграция; сценарий (генерация + фиксация полей) повторён идентично. Удаление легаси-методов оружия/брони — предложение владельцу (см. GAP).
2. **CloneForm → глубокая копия Effects** (поверхностная копия делила список — мутация ControlType меняла ОБЕ формации, fingerprints ложно равнялись).
3. **A3-морфология**: Slot-совпадение не требуется для WeaponMain/WeaponOff (у оружия Slot всегда WeaponMain — домашний слот класса; размещение определяет словарь), броня обязана совпадать.

Таким образом, полная регрессия НЕ объявляется безусловно зелёной: 32/34 stable + 2 флаки-остатка с воспроизводимыми доказательствами их независимости от этапа-15.

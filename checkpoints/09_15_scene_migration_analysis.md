### 1.2. Обе .tscn-сцены — пустые скрипт-хосты

- `scenes/GameWorld.tscn` = один `Node2D` + скрипт GWC. **Ноль детей.**
- `scenes/MainMenu.tscn` = один `Control` (FullRect) + скрипт MainMenuController.
- Весь визуальный дерево — от корня до последнего Label — строится C#-кодом.

### 1.3. Паттерны композиции по слоям

| Подсистема | Как строится сейчас | Статика/динамика |
|------------|---------------------|------------------|
| **UI-окна (~20)** | `partial class X : Control` + `[Inject]` + `BuildUI()` — `new`/AddChild/anchors вручную | Каркас статичен, списки/слоты динамичны |
| **HUD-панели** (Hotbar 654, BodyStatus 549, Doll 564) | то же | динамичны (данные сима) |

| **Тайлмап** | TileMapGenPhase (TileMapLayer) + SceneBuilder (биом-спрайты) + SurfaceTransitionRenderer | runtime-данные мира |
| **MainMenu** | MainMenuController + UIFactory (16 вызовов) | статичен |
| **Entry-фазы (17)** | SceneOrchestrator — чистая оркестрация | — |
| **QA-хуки (44 SimDebug)** | C#-классы, читают env | — |

### 1.4. Документированное архитектурное решение (ВАЖНО)

`docs_v2/07_ui/UI_DESIGN.md` **§7 «UI Builder Pattern»** прямо предписывает
сборку UI из кода, обоснования §7.4:
1. «Воспроизводимость — UI собирается из кода, а не из бинарного файла сцены…
   упрощает AI-агентный цикл».
2. Git-совместимость (diff в исходниках).
3. Тестируемость дескрипторов headless.
4. Портабельность (смена движка = смена UI Builder).

**Два уточнения к обоснованию:**
- Пункт 1 частично устарел: .tscn в Godot 4 — **текстовый** формат (не бинарный),
  git-friendly и мерджится. Формулировка «бинарного файла сцены» неверна для 4.x.
- §7.2–7.3 описывают декларативный слой `UIElementDescriptor` — **он так и не был
  реализован**: реальные окна строят Godot-нодами напрямую (BuildUI), т.е. слой
  Adapter связан с Godot сильнее, чем обещает док.

## 2. Классификация: что вообще ДОЛЖНО быть сценой

Godot-canonical разбиение (не всё «в сцены» — это не цель, а инструмент):

| Категория | Сцена? | Обоснование |
|-----------|--------|-------------|
| Статичный каркас окон (рамки, заголовки, layout-контейнеры, футеры) | ✅ да | редактор, визуальная настройка, меньше бойлерплейта |
| Динамические списки/слоты/строки (инвентарь, книга техник, торговля) | ❌ код (+ опц. row-template сцена) | количество = данные сима |
| Шаблоны визуала сущностей (NPC-роли, виды зверей, труп, снаряд, предмет на земле) | ✅ да (PackedScene-шаблон + Instantiate) | канон для спавна; открывает художникам анимации/шейдеры/партиклы |
| Тайлмап/террейн | ❌ никогда | runtime-данные (особенно procgen) |
| Тема (Theme) | ✅ .tres-ресурс | вместо `ParchmentTheme.Create()` в каждом окне |
| GWC (god-controller 2607 LOC) | ⚠️ ортогонально | «сцена» тут = декомпозиция на дочерние ноды-скрипты, отдельный рефакторинг |
| QA SimDebug (44) | ❌ | тестовые хуки |
| Entry-фазы | ❌ | оркестрация |

## 3. Оценка сложности по ярусам

### Ярус 1 — лёгкий: статичные окна (~0,5–1 день на окно)

`QuestWindow` (255), `HotkeysWindow` (264), `DialogueWindow` (350),
`EventLogWindow` (400), `CharacterSheetWindow`, `CultivationWindow` (600).

Паттерн миграции одного окна:
1. Собрать в редакторе .tscn с тем же деревом (или сгенерировать .tscn
   текстом — формат простой, узлы уже именованы в коде).
2. Скрипт окна остаётся тем же классом; BuildUI() → ссылки на ноды
   (`GetNode`/`%unique_names`/`[Export]`).
3. DI не меняется (`_Ready` → GameBoot.Container).
4. Тема: Theme-ресурс на корне сцены вместо `ParchmentTheme.Create()`.

Риски: точный перенос anchors/offsets (сейчас заданы числами в коде —
перенос механический, но без визуального сверения легко ошибиться);
QA-симы зовут `Toggle()` — не затрагиваются, если класс сохранён.

### Ярус 2 — средний: смешанные окна и HUD (~1–2 дня на окно)

`InventoryWindow` (1031), `TechniqueBookWindow` (953), `CheatPanel` (780),
`ItemContextMenu` (658), `HotbarPanel` (654), `TradeWindow` (617),
`LootWindow` (591), `CharacterDollPanel` (564), `BodyStatusPanel` (549).

Каркас → .tscn; строки/слоты/чипы — код (или мини-сцена-шаблон строки).
Здесь главный объём работы: ~30–50% LOC этих файлов — layout-бойлерплейт,
он удалится, но каждый перенос требует сверки с текущим видом.

### Ярус 3 — сложный/спорный: сущности и GWC

- **Слой шаблонов сущностей**: вместо `new Sprite2D { Texture = ... }` —
  `PackedScene` на архетип (npc_guard, animal_wolf, corpse, projectile, …)
  + `Instantiate()`. Рендереры (11 классов, ~3 400 LOC) превращаются в
  «спавнер + биндинг полей». Работа ~1–2 недели. Выгода: редактируемые
  визуалы (анимации, шейдеры), палитра для procgen.
- **ProceduralSpriteGenerator** НЕ мигрирует (это генерация текстур, не нод) —
  остаётся как fallback/прототипирование; шаблоны сцен могут ссылаться на его
  текстуры так же, как сейчас на кэш.
- **GWC**: сцена сама по себе его не улучшит; нужна декомпозиция на дочерние
  ноды (HUD-root, World-root, Cameras, Windows-root). Это отдельный
  рефакторинг ~1–2 недели, решает проблему god-controller, а не «код vs сцены».

### Не подлежит миграции

Тайлмап (runtime-данные), Entry-фазы, QA SimDebug, Core/Modules (движок-agnostic
по архитектуре — там сцен нет и не должно быть).

## 5. Влияние на процедурную генерацию уровней (дальние планы)

1. **Procgen не мешает сценам, а требует их.** Канонический Godot-procgen —
   .tscn-шаблоны (комнаты/чанки/сущности) + `Instantiate()` + код-склейка.
   Текущее состояние (**0 PackedScene**) означает: procgen пришлось бы писать
   на 100% руками, как ProceduralSpriteGenerator для текстур.
2. **Что уже готово для procgen**: TileMapLayer-конвейер, SceneBuilder-страты,
   генераторы мира/популяции (GenerateStartup, «пояс жизни» L500) — всё
   runtime-композиция, она и есть основа procgen.
3. **Чего не хватает**: слоя шаблонов (Ярус 3) — именно он станет «палитрой
   комнат/декора» для генератора уровней.
4. **Вывод**: миграция Яруса 3 (шаблоны сущностей) — **пререквизит** будущей
   процедурной генерации уровней; миграция UI (Ярусы 1–2) ортогональна procgen
   и делается только ради редактора/художников.

## 6. Риски миграции

1. **Точность переноса layout** — anchors/offsets числами из кода; без
   скриншот-базелина легко незаметно сдвинуть. Нужно: скриншот-базелин до
   миграции (Xvfb-рендер уже освоен в песочнице).
2. **Тема**: мёртвый `resources/themes/ParchmentTheme.tres` существует, но
   код использует `ParchmentTheme.Create()`. При миграции — один Theme-ресурс
   на проект, иначе расползание стилей.
3. **AI-агентный цикл** (причина исходного решения §7.4): правки .tscn хуже
   генерируются агентом, чем C#-код; мердж-конфликты .tscn неприятнее.
   Частично компенсируется: .tscn текстовый, узлы уже именованы.
4. **44 QA SimDebug** зовут API окон напрямую — не ломаются при сохранении
   классов/методов; но смена дерева (появление промежуточных нод) требует
   проверки `GetNode`-путей в тестах.
5. **R17 save** — не затрагивается: ISaveable-состояние — данные, не дерево.
6. **INP-1 модальные хелперы** — проверяют `Visible`/`IsOpen` у полей GWC:
   не затрагиваются, пока окна остаются теми же объектами.

## 7. Выводы

1. Проект — **монолит кодовой композиции**: 2 пустые сцены, 0 PackedScene,
   весь UI/рендер/спрайты из кода. Это осознанное решение (docs_v2 §7),
   но частично по устаревшим основаниям (.tscn — текст) и слой
   UIElementDescriptor из доки не реализован.
2. Миграция **возможна поярусно**, каждый ярус независим: UI-окна →
   шаблоны сущностей → тема → (опц.) GWC. Полная стоимость ~4–7 недель.
3. **Для процедурной генерации уровней** ценен только Ярус 3 (шаблоны
   сущностей) — он же открывает художественный пайплайн. Ярусы 1–2 —
   качество жизни редактирования UI.
4. **Рекомендация (когда придёт время)**: гибрид — .tscn для каркасов окон
   и шаблонов сущностей, код для данных/списков/тайлов; Theme в .tres;
   до начала — скриншот-базелин + обновление UI_DESIGN.md §7. Ничего из
   этого сейчас НЕ делается (требование пользователя: только анализ).
